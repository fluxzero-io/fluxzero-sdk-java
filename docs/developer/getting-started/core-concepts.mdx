# Your code in Fluxzero

Fluxzero applications are built from plain messages, immutable models and small handler methods. Fluxzero supplies
delivery, persistence, routing, retries, observability and scaling.

The most important building blocks are:

| Concept | Purpose | Example |
|---|---|---|
| Command | Requests a state change | `RenameProject` |
| Model | Independently stored domain state | `Project`, `Task` |
| Query | Requests information | `FindOpenTasks` |
| Event | Announces an accepted model update | `RenameProject` |
| Handler | Reacts to a message or HTTP request | `@HandleEvent`, `@HandleGet` |
| Test fixture | Tests behavior without infrastructure code | `fixture.whenCommand(...)` |

## Start with actions

Model what a user or process wants to do as a command. A command can own validation, authorization, assertions and its
state transition:

<Tabs>
  <TabItem label="Java">

```java
public record RenameProject(ProjectId projectId,
                            @NotBlank String name) {
    @AssertLegal
    void assertOwner(Project project, Sender sender) {
        if (!project.ownerId().equals(sender.userId())) {
            throw new UnauthorizedException("Not allowed to rename project");
        }
    }

    @Apply
    Project apply(Project project) {
        return new Project(projectId, name, project.ownerId());
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
data class RenameProject(
    val projectId: ProjectId,
    @field:NotBlank val name: String
) {
    @AssertLegal
    fun assertOwner(project: Project, sender: Sender) {
        if (project.ownerId != sender.userId()) {
            throw UnauthorizedException("Not allowed to rename project")
        }
    }

    @Apply
    fun apply(project: Project) =
        Project(projectId, name, project.ownerId)
}
```

  </TabItem>
</Tabs>

Publishing this command is enough. Because Fluxzero can resolve its `ProjectId`, its required `Project` parameter and
its `@Apply` return type, no ceremonial command handler is needed:

```java
Project renamed = Fluxzero.sendCommandAndWait(
        new RenameProject(projectId, "Launch"));
```

Use an explicit `@HandleCommand` when the action needs orchestration around the model update. Such a handler can call
`Fluxzero.assertAndApply(update)` once.

## Models

`@Model` marks independently stored domain state:

<Tabs>
  <TabItem label="Java">

```java
@Model(searchable = true)
public record Project(@EntityId ProjectId projectId,
                      String name,
                      UserId ownerId) {
}

public final class ProjectId extends Id<Project> {
    public ProjectId(String value) {
        super(value, "project-");
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@Model(searchable = true)
data class Project(
    @EntityId val projectId: ProjectId,
    val name: String,
    val ownerId: UserId
)

class ProjectId(value: String) : Id<Project>(value, "project-")
```

  </TabItem>
</Tabs>

Each model ID is its own persistence and lifecycle boundary. Its event stream, cache, snapshots and direct search
document are enabled independently through `@Model` settings. The exact
`Id.toString()` value is its persisted identity.

Models are event-sourced by default. Set `eventSourced = false` when current state should load from the direct
document instead. Updates are still stored as model events and published according to `eventPublication`; the option
only changes how current state is loaded.

```java
@Model(eventSourced = false, searchable = true)
public record Product(@EntityId ProductId productId,
                      String name,
                      BigDecimal price) {
}
```

Direct documents are updated as part of model-commit completion. A successful command is therefore immediately
visible through direct model loading and search.

## Create, update and delete

An `@Apply` method returns the target model state:

```java
public record CreateProject(ProjectId projectId,
                            String name) {
    @Apply
    Project apply(Sender sender) {
        return new Project(projectId, name, sender.userId());
    }
}

public record DeleteProject(ProjectId projectId) {
    @Apply
    Project apply(Project project) {
        return null;
    }
}
```

- A factory without the current model creates it.
- A method receiving the current model updates it.
- Returning `null` logically deletes it and still stores the update event.
- `void` model applies are rejected; model transitions are immutable and explicit.

`@AssertLegal` and `@InterceptApply` run before `@Apply`. All applicable methods participate in one commit. If an
assertion fails, no model event, document or relationship update is committed.

Keep `@Apply` deterministic. It is also used when Fluxzero event-sources the model later. Do I/O and external side
effects in message handlers, not in state transitions.

## One action, multiple models

An action may read or update unrelated models without placing them in one permanent object tree:

```java
public record ReserveItem(OrderId orderId,
                          InventoryId inventoryId,
                          int quantity) {
    @AssertLegal
    void inventoryAvailable(Inventory inventory) {
        if (inventory.available() < quantity) {
            throw new IllegalStateException("Insufficient stock");
        }
    }

    @Apply
    Order apply(Order order) {
        return order.reserve(quantity);
    }

    @Apply
    Inventory apply(Inventory inventory) {
        return inventory.reserve(quantity);
    }
}
```

Fluxzero resolves direct targets from typed IDs and commits the resulting events, current documents, snapshots and
relationship deltas as one model commit. If the payload contains two IDs of the same model type, qualify the parameter:

```java
@Apply
Account debit(@Association("sourceId") Account source) { ... }
```

## Relationships instead of ownership

Use `@ParentId` when independently stored models form a navigable graph:

```java
@Model(searchable = true)
public record Task(@EntityId TaskId taskId,
                   @ParentId(path = "tasks") ProjectId projectId,
                   String description,
                   boolean completed) {
}
```

Changing only `projectId` moves a task. The parent, siblings and children do not need to be loaded. The stable `path`
is optional; without it, Fluxzero still stores the relation but does not automatically place the child in a stitched
tree document.

Parents and further ancestors can be injected into model assertions, apply interceptors and applies. Use
`@Association("path")` when more than one relation could match:

```java
@AssertLegal
void assertProjectOpen(Task task,
                       @Association("tasks") Project project) {
    if (project.closed()) {
        throw new IllegalStateException("Project is closed");
    }
}
```

Search can follow current relationships in either direction. It can, for example, find `Task` documents whose project
matches a project constraint, without first materializing a whole-project read model.

## Embedded members

Not every value needs an independent lifecycle. Use `@Member` inside a model for state that really lives, loads,
searches and disappears with that model:

```java
@Model(searchable = true)
public record Invoice(@EntityId InvoiceId invoiceId,
                      @Member List<InvoiceLine> lines) {
}

public record InvoiceLine(@EntityId LineId lineId,
                          String description,
                          BigDecimal amount) {
}
```

The invoice and lines above intentionally share one stream, cache entry, document and lifecycle. Prefer a separate
`@Model` plus `@ParentId` as soon as a child is independently updated, searched, moved, retained or erased.

## Loading and exact event state

Load current state by typed ID:

```java
Entity<Project> entity = Fluxzero.loadModel(projectId);
Project project = entity.get();
```

In an event or notification handler, a directly affected model can be injected:

```java
@HandleEvent
void on(RenameProject event,
        Project project,
        Entity<Project> entity) {
    // Both represent the project exactly after this event's model-commit substep.
}
```

This is historical event-boundary injection, not an arbitrary current-state lookup. It only applies to events carrying
a model-commit boundary. `Entity<T>` is useful for logical delete events because it can represent an absent value; a
bare non-null `T` only matches while the model exists.

## Queries and search

Queries are plain request objects handled with `@HandleQuery`:

```java
public record FindProjects(String term) {
}

public final class ProjectQueries {
    @HandleQuery
    CompletableFuture<List<Project>> handle(FindProjects query) {
        return Fluxzero.search(Project.class)
                .lookAhead(query.term(), "name")
                .fetchAsync(50, Project.class);
    }
}
```

The direct collection of a searchable model is synchronous with its model commit. A whole-tree graph projection is a
separate read optimization and is asynchronous by default. Choose `GraphProjectionCompletion.AWAIT` for an operation
whose result must not be released until affected root projections have crossed its state boundary.

## Events and handlers

Every accepted update returned by `@Apply` is the model event. Fluxzero stores it in each affected modelstream and
publishes it once to the global event log when configured to publish:

```java
public final class ProjectNotifications {
    @HandleEvent
    void on(RenameProject event, Project project) {
        // Call an external system or publish another message here.
    }
}
```

An event that targets several models is not globally duplicated. Each stream gets a membership to the same action
payload.

## Tests

`TestFixture` runs the same assertions, applies and handlers as production:

```java
TestFixture.create()
        .givenCommands(new CreateProject(projectId, "Initial"))
        .whenCommand(new RenameProject(projectId, "Launch"))
        .expectThat(fluxzero -> assertEquals(
                "Launch",
                Fluxzero.loadModel(projectId).get().name()))
        .expectEvents(new RenameProject(projectId, "Launch"));
```

Use `whenCommand(...)` for end-to-end behavior and `whenApplying(...)` for direct SDK operations. Integration tests can
run the same flow against a real Fluxzero runtime.

## Legacy applications

Fluxzero 1.x continues to support `@Aggregate` and its loading APIs for existing persisted applications. New
applications and new domain state should use `@Model`; `@Model` with `@Member` covers the intentional single-stream
case too. The aggregate API is scheduled for Java deprecation in Fluxzero 2.0 because migrating existing aggregate
streams is a persistence migration, not a source-only annotation change.
