This Developer Guide is an optional look inside the code. You do not need to write or read code to build with an agent.
For the practical building process, see [the introduction](/docs/getting-started/introduction).

Fluxzero is the cloud that runs your application. Its SDK lets you describe what your product does: the actions people can take, the information it remembers,
and the rules it follows. Your coding agent can build this in Java or Kotlin, or you can write the code yourself.

The main building blocks are **commands**, **queries**, **models**, **handlers**, and **tests**.
Fluxzero handles message delivery and persistence around them.

## Commands

A command asks the application to do something: create a project, complete a task, or send a notification.
It is a plain object containing the information needed for that action.

For an action that changes stored state, an `@Apply` method describes the change:

<Tabs>
  <TabItem label="Java">

```java
public record CompleteTask(TaskId taskId) {
    @Apply
    Task complete(Task task) {
        return task.withCompleted(true);
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
data class CompleteTask(val taskId: TaskId) {
    @Apply
    fun complete(task: Task) = task.copy(completed = true)
}
```

  </TabItem>
</Tabs>

Fluxzero finds the task using its typed ID and applies the command. Input constraints such as `@NotBlank` validate
what came in; `@AssertLegal` methods express business rules such as “only the assignee may complete this task”.
If the action is rejected, its state change is not stored.

## Models

A model is information your application remembers, such as a task, a booking, or a customer. It has an identity and
can change over time. `@Model` tells Fluxzero to store it:

<Tabs>
  <TabItem label="Java">

```java
@Model
public record Task(@EntityId TaskId taskId, String name, @With boolean completed) {
}

public final class TaskId extends Id<Task> {
    public TaskId(String id) {
        super(id);
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@Model
data class Task(
    @EntityId val taskId: TaskId,
    val name: String,
    val completed: Boolean
)

class TaskId(id: String) : Id<Task>(id)
```

  </TabItem>
</Tabs>

Models are immutable: an update returns a new value. Java's `@With` comes from Lombok; Kotlin data classes provide `copy`.
By default, Fluxzero remembers their accepted changes as events
and uses those events to reconstruct state. This is called **event sourcing**.

Models can be related. A task can point to a project using `@Parent`, while remaining a model in its own right.
For example, adding a parent ID connects each task to a project:

<Tabs>
  <TabItem label="Java">

```java
@Model
public record Task(@EntityId TaskId taskId, @Parent ProjectId projectId,
                   String name, @With boolean completed) {
}

@Model
public record Project(@EntityId ProjectId projectId, String name) {
}

public final class ProjectId extends Id<Project> {
    public ProjectId(String id) { super(id); }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@Model
data class Task(
    @EntityId val taskId: TaskId,
    @Parent val projectId: ProjectId,
    val name: String,
    val completed: Boolean
)

@Model
data class Project(@EntityId val projectId: ProjectId, val name: String)

class ProjectId(id: String) : Id<Project>(id)
```

  </TabItem>
</Tabs>

A **Graph** lets you explore related models together, for example a project and its tasks.

## Queries

A query asks for information without changing it. Like a command, it is a plain object. Its handler returns the answer:

<Tabs>
  <TabItem label="Java">

```java
public record GetTask(TaskId taskId) implements Request<Task> {
    @HandleQuery
    Task handle() {
        return Fluxzero.loadModel(taskId).get();
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
data class GetTask(val taskId: TaskId) : Request<Task> {
    @HandleQuery
    fun handle(): Task? = Fluxzero.loadModel(taskId).get()
}
```

  </TabItem>
</Tabs>

`Request<Task>` declares the result type. Queries can also search and filter many models, for example to find your
open tasks. A handler can check who is asking before returning information.

## Handlers

Handlers are methods that respond to messages. Their annotation says what they handle:

| Annotation | Responds to |
|---|---|
| `@HandleCommand` | A request to perform an action |
| `@HandleQuery` | A request for information |
| `@HandleEvent` | Something that has happened |
| `@HandleGet`, `@HandlePost` | An HTTP request |
| `@HandleSchedule` | A scheduled message becoming due |

A model command with `@Apply` already has automatic handling. Add an explicit command handler when an action needs
other work, such as calling an external service.

### Events

After an accepted model change, Fluxzero normally publishes the applied command payload as an **event**.
The command asked for the change; the event tells other parts of the application it happened.

For example, a handler can react when a task is completed:

<Tabs>
  <TabItem label="Java">

```java
@HandleEvent
void on(CompleteTask event, Task task) {
    Fluxzero.sendCommand(new NotifyAssignee(task.taskId()));
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@HandleEvent
fun on(event: CompleteTask, task: Task) {
    Fluxzero.sendCommand(NotifyAssignee(task.taskId))
}
```

  </TabItem>
</Tabs>

Several handlers can react to the same event. This lets you add behavior without putting it all in the original
command. The injected task represents the state at that event.

### HTTP and scheduled work

An HTTP endpoint is a handler too:

<Tabs>
  <TabItem label="Java">

```java
@HandleGet("/hello")
String hello() {
    return "Hello, world!";
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@HandleGet("/hello")
fun hello() = "Hello, world!"
```

  </TabItem>
</Tabs>

Fluxzero handles routing and response formatting. A handler can send a command or query to expose your app's behavior.

Scheduled messages use the same idea: schedule a reminder for tomorrow and handle it with `@HandleSchedule` when it
is due. You can cancel or replace a schedule when the user's plans change.

Register separate handler objects with your application; Spring applications can use `@Component` for discovery.
The [configuration guide](/docs/guides/configuration/configuring-fluxzero) explains registration.

## Tests

`TestFixture` runs your commands and handlers locally. Tests describe a **given → when → then** flow, without setting
up a database or mocking the platform. Inputs and expected results can live in reusable JSON files:

<Tabs>
  <TabItem label="Java">

```java
TestFixture.create()
        .givenCommands("/task/create-task.json")
        .whenCommand("/task/complete-task.json")
        .expectEvents("/task/complete-task.json");
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
TestFixture.create()
    .givenCommands("/task/create-task.json")
    .whenCommand("/task/complete-task.json")
    .expectEvents("/task/complete-task.json")
```

  </TabItem>
</Tabs>

Tests can also query the resulting state, check failures, call HTTP endpoints, or advance time to trigger scheduled
work. The [to-do tutorial](/docs/tutorials/first-app) builds each of these pieces step by step, including the JSON files.

For more detail on any building block, continue with the [technical guides](/docs/guides).
