Fluxzero offers built-in support for handling sensitive information with care using the `@ProtectData` and
`@DropProtectedData` annotations.

These tools help prevent sensitive fields (e.g., passwords, SSNs, tokens) from being unnecessarily stored, logged, or
retained — supporting compliance with data protection standards like **GDPR** and **ISO 27001**.

---

## @ProtectData: mark sensitive fields

To prevent a field from being stored with the rest of a message payload, annotate it with `@ProtectData`:

<Tabs>
  <TabItem label="Java">
    ```java
    public record RegisterCitizen(String name,
                                  @ProtectData String socialSecurityNumber) {
    }
    ```
  </TabItem>
  <TabItem label="Kotlin">
    ```kotlin
    data class RegisterCitizen(
        val name: String,
        @ProtectData val socialSecurityNumber: String
    )
    ```
  </TabItem>
</Tabs>

When this message is dispatched, the `socialSecurityNumber` will be:

- **Offloaded** to a separate data vault when the message is published externally
- **Redacted** from the main payload (not visible in logs or message inspectors)
- **Re-injected** automatically when the message is handled

This happens transparently — you can access the field as usual in handler methods.

If a message is handled only by a local handler with `logMessage = false`, the original value remains in memory and is
passed directly to that handler without a KV write or read. External fallback and `logMessage = true` keep the normal
vault-backed behavior. `@LocalOnly` prevents external command dispatch; it does not suppress durable domain writes
performed by the handler.

### Independent Model events

Automatic `@Model` commands and explicit `assertAndApply` updates also protect their stored and published events,
including records, ordinary objects, and replacement payloads returned by `@InterceptApply`. A local Model commit is
a durable write: its protected values must be available in the vault before the commit is sent. Unchanged restored
values keep their references, even after erasure; a genuinely changed value receives a new reference. JSON property
names, aliases, and configured naming strategies are respected.

Reconstructing a Model restores retained values before resolving targets and applying stored events. It does not run
command assertions/interceptors, write protected values, or execute `@DropProtectedData`. An erased value is `null`,
so replay applies must tolerate missing private data. A vault read failure fails reconstruction instead of caching an
incomplete Model. `@ProtectData` does not redact secrets deliberately copied into Model state, documents or snapshots.

The built-in Jackson serializer supports standard bean properties, configured property names, aliases and nested
unwrapped properties. Custom codecs, modified property writers, dynamic filters/any-getters and type/root wrappers
require an explicit, safe `Serializer.serializedPropertyPaths` implementation matching their wire representation.
Other serializer implementations must provide this capability too; the default does not guess property names.
Unsupported mappings and formats fail before the Model commit rather than leaving private values in stored bytes.

## @DropProtectedData: remove when done

If the protected data should only be retained **temporarily**, annotate the handler method with `@DropProtectedData`:

<Tabs>
  <TabItem label="Java">
    ```java
    @HandleCommand
    @DropProtectedData
    void handle(RegisterCitizen command) {
        validate(command.getSocialSecurityNumber());
        ...
    }
    ```
  </TabItem>
  <TabItem label="Kotlin">
    ```kotlin
    @HandleCommand
    @DropProtectedData
    fun handle(command: RegisterCitizen) {
        validate(command.socialSecurityNumber)
        ...
    }
    ```
  </TabItem>
</Tabs>

Once this handler completes:

- The injected `socialSecurityNumber` is permanently deleted from storage, or discarded from memory for a local-only
  dispatch.
- Future replays will deserialize the message with that field omitted.

<Aside type="caution">
This mechanism ensures sensitive fields are usable just-in-time and discarded thereafter.
</Aside>

---

## Use cases

- Temporary use of sensitive tokens or credentials
- Compliance with **data minimization** and **retention policies**
- Preventing accidental exposure in logs or audits

---

## Replays and protected data

During replays, if a message with protected fields is re-invoked **after** data has been dropped, those fields will be
missing or set to `null`.

<Aside type="note">
Design your handlers to tolerate this by making such fields optional or guarding usage.
</Aside>

## Missing protected data policies

Handlers can choose how to respond when protected values referenced by a message are no longer available:

<Tabs>
  <TabItem label="Java">
    ```java
    @HandleEvent(onMissingProtectedData = MissingProtectedDataPolicy.SKIP)
    void handle(CitizenRegistered event) {
        ...
    }
    ```
  </TabItem>
  <TabItem label="Kotlin">
    ```kotlin
    @HandleEvent(onMissingProtectedData = MissingProtectedDataPolicy.SKIP)
    fun handle(event: CitizenRegistered) {
        ...
    }
    ```
  </TabItem>
</Tabs>

The available policies are:

- `HANDLE`: invoke silently with unavailable fields set to `null` (SDK default)
- `WARN`: log a warning and invoke with unavailable fields set to `null`
- `SKIP`: skip only this handler invocation and advance tracking normally
- `FAIL`: fail through the consumer's normal error handling
- `DEFAULT`: inherit from the consumer or application configuration

The effective policy is resolved from the handler, consumer, builder, application property, and finally the SDK
default. Configure the application fallback with
`DefaultFluxzero.builder().onMissingProtectedData(...)` or:

```properties
fluxzero.dataProtection.onMissingProtectedData=WARN
```

For environment variables, both `FLUXZERO_DATA_PROTECTION_ON_MISSING_PROTECTED_DATA` and the compact Spring-style
`FLUXZERO_DATAPROTECTION_ONMISSINGPROTECTEDDATA` are supported.

When tracking metrics are enabled, `SKIP` emits an `IgnoreMessageEvent` with reason `missingProtectedData`.

---

## Notes

- Only **fields** can be annotated with `@ProtectData` (not method parameters).
- Dropping data is **irreversible**. Make sure all processing is complete before it is removed.
- Support for nested structures is currently limited — annotate each sensitive field explicitly.
