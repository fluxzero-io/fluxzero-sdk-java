Every useful application remembers something. An order records what a customer bought. A payment workflow remembers
which confirmation it is waiting for. A dashboard keeps a current summary assembled from several sources.

Fluxzero supports all three without requiring every kind of state to look like a database table or a domain object.
The important first question is not *where can I put this value?*, but *what role does this state play?*

There are three native ways to persist application state:

| State mechanism | Use it for | Fluxzero owns |
| --- | --- | --- |
| **Models and Graphs** | Domain objects and business facts | Identity, changes, relationships, history and atomic Model operations |
| **Stateful handlers** | Progress across messages and current views assembled by handlers | Matching messages to stored handler instances and persisting their returned state |
| **Custom documents or key-value state** | Application-owned read models, mappings, caches and supporting state | Durable document or key-value storage; your handler owns the lifecycle |

These mechanisms complement one another. A payment can be a Model, the conversation with its provider can be a
Stateful handler, and an operational dashboard can be a custom document. Choose one authoritative owner for each fact
instead of keeping the same truth independently in several stores.

## Models and Graphs for domain state

Use a Model for something the business recognizes and changes independently: an account, order, booking or task.
Each Model has its own identity and lifecycle. `@Parent` relationships connect Models, and a Graph lets you navigate
that connected state at one consistent read boundary.

Models are the standard choice for domain objects. They are also the right place for rules that decide whether a
business change is allowed. One action can read and update several Models atomically without merging their lifecycles.

[Learn how Models and Graphs represent domain state](/docs/guides/modeling-and-persistence/models-and-graphs).

## Stateful handlers for process memory and combined views

Sometimes state exists because handling one message is not enough. A process may send a request now, receive the
answer later and need to remember which request that answer belongs to. A Stateful handler is both a message handler
and a persisted state object: Fluxzero finds the right instance through its associations and stores the new instance
returned by the handler.

That same mechanism is useful for current views assembled from several inputs. A Stateful handler can react to events
or document and Model changes, combine the latest information it needs, and expose the resulting state as a searchable
view. The view remains a projection; domain decisions should still use their authoritative Models.

- [Use Stateful handlers for long-running processes](/docs/guides/modeling-and-persistence/stateful-handlers).
- [Build current searchable projections from several sources](/docs/guides/modeling-and-persistence/current-projections).

## Custom documents or key-value state for explicit storage

A message handler can also own state directly. Use the <Jdoclink className="DocumentStore" /> for structured current
documents that need direct lookup, indexing or search. This is a natural fit for an application-owned read model,
an imported catalogue or a denormalized integration view whose lifecycle is deliberately controlled by one writer.

The <Jdoclink className="KeyValueStore" /> remains available for simple values addressed by one key. It is a legacy
Runtime API; prefer the document store for new structured state because it supports querying, indexing, updates and
document lifecycle features. With either API, your handler owns when the state is written, replaced and removed.

[Store and query custom documents](/docs/guides/modeling-and-persistence/document-index-and-search).

<Aside type="tip" title="Start with the state owner">
If users act on it as a business fact, start with a Model. If it remembers unfinished work between messages, start
with a Stateful handler. If it is a derived or supporting value with an application-owned lifecycle, start with a
custom document. Reach for key-value storage only when a simple key lookup is genuinely the whole requirement.
</Aside>

## Let each form do one job

The three forms often appear in one feature, but they should not become competing sources of truth:

- A Model records that a payment was accepted.
- A Stateful handler remembers a pending provider request and its retry progress.
- A custom document combines payments, customers and risk signals for an operational screen.

The command that accepts a payment reads the Model, not the dashboard row. The workflow updates the Model through a
command when an external result becomes a business fact. The dashboard can be rebuilt from its sources when needed.
Keeping those roles separate makes the behavior easier to explain, test and recover.
