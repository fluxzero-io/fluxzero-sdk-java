Every `@Model` has an independent persisted identity. The annotation configures how that model is loaded, cached,
snapshotted, searched and conflict-checked:

```java
@Model(
    eventSourced = true,
    searchable = true,
    snapshotPeriod = 1000)
record Account(
        @EntityId AccountId accountId,
        Money balance) {
}
```

The persisted key is exactly `accountId.toString()`. A model name or Java type is not concatenated into the identity.

## Event-sourced models

Event sourcing is the default:

```java
@Model
record Account(@EntityId AccountId accountId, Money balance) {
}
```

Each applied update is stored in this account's model stream. Loading reconstructs the account by replaying its
`@Apply` methods, optionally starting at a snapshot or checkpoint.

Independent models prevent unrelated histories from accumulating in one enormous stream. An order line, payment
attempt or short-lived process can keep its own small history while still participating in one multi-model commit.

## Document-based models

Set `eventSourced = false` to make the current direct document the normal load source:

```java
@Model(
    eventSourced = false,
    searchable = true,
    collection = "countries")
record Country(
        @EntityId CountryId countryId,
        String name) {
}
```

`eventSourced` controls the **load path**, not whether updates become events. Applied updates are still stored and
published by default. This preserves auditing, exact event-handler boundaries and the option to change loading strategy
later.

The direct searchable document is synchronously maintained with the model commit. After a successful command result,
an immediate direct search can observe the changed model.

<Aside type="caution">
A document-based model needs a current document. Normally that means `searchable = true`; a non-searchable child with
an explicit `@Parent(path = "...")` can instead load from its private graph-component document.
</Aside>

## Event storage and publication

`eventPublication` determines whether an apply produces an event:

- `ALWAYS` stores/publishes the applied update;
- `IF_MODIFIED` suppresses it when the resulting model did not change;
- `NEVER` stores no model event but can still commit a current document;
- `DEFAULT` inherits the next broader setting.

`publicationStrategy` controls where a produced event goes:

- `STORE_AND_PUBLISH` links it to the model stream and publishes it once globally;
- `STORE_ONLY` links it to model streams without global publication;
- `PUBLISH_ONLY` publishes it without adding a model-stream membership;
- `DEFAULT` inherits configuration.

An event-sourced model may only change through `STORE_AND_PUBLISH` or `STORE_ONLY`, because its next load must be able
to reconstruct that state. Fluxzero rejects create, update and logical-delete transitions configured as
`PUBLISH_ONLY` or `eventPublication = NEVER` before commit. A publication-only no-op remains valid, and a
document-based model can still change without storing the event because its current document is the load source.

For an event targeting several models, each stream receives a lightweight membership. The full payload remains inline
for ordinary small target sets; large multi-target payloads may be stored once and shared. Hard deletion removes only
the selected stream membership, and the shared payload is deleted only after no surviving membership refers to it.
The global event log is independent.

## The model commit package

The SDK evaluates one complete model commit and submits:

- the original applied events;
- target model memberships;
- expected/read state boundary;
- resulting direct documents when required;
- snapshots or checkpoints when due;
- relation additions and closures;
- conflict and graph-projection completion policies.

The runtime assigns monotone, time-derived `stateIndex` values and commits the co-located event store, model streams,
heads, relations, commit result and projection signals atomically in its JDBC transaction.

The runtime completes direct documents and snapshots before it releases a successful model-commit result. When event
and search storage use separate runtime-managed databases, the core action retains the exact serialized
materialization until the fenced search write succeeds. A retry or the runtime's restart worker reapplies that original
package; application code is never re-evaluated to repair an already committed action. Materialized whole-root graph
projections may continue asynchronously unless `AWAIT` was selected.

## Searchable models

`searchable = true` gives every model its own direct current document:

```java
@Model(searchable = true, collection = "line-items")
record LineItem(
        @EntityId LineItemId lineItemId,
        @Parent(path = "lines") OrderId orderId,
        ProductId productId) {
}
```

This document is authoritative for direct search and for document-based loading. It is not the asynchronously stitched
root graph.

`searchable = false` controls only this independent collection. A child with an explicit `@Parent(path = "...")`
still supplies a private current document to virtual and materialized graph composition. Without an explicit path,
Fluxzero stores no graph-component document and performs no extra document write.

You can additionally:

- join current direct documents through `whereAncestor(...)` and `whereDescendant(...)`;
- search a complete JSON graph with `searchGraph(Root.class)`, using a materialized projection when configured and
  otherwise stitching live;
- configure `graphProjection = @GraphProjection(...)` for a durable, materialized root document.

## Caching

Models use a shared current-state cache and an action-local cache:

- a current local hit requires no head-validation round trip;
- one namespace-level long poll tracks durable model updates;
- remote updates fence or refresh only affected cached IDs;
- document-based models are refreshed from their direct document;
- event-sourced models reuse a cached replay base and load only the missing suffix;
- hard deletion evicts the ID without retaining private tombstone state in the SDK cache.

Use `FluxzeroBuilder.withModelCache(cache)` for a dedicated model cache, or
`FluxzeroBuilder.disableAutomaticModelCaching()` to disable both shared model caching and its update tracker.

The default `cachingDepth` retains the previous revision needed by common event-handler comparison logic. Configure a
larger depth only when the application actively uses deeper `Entity.previous()` chains.

Disable shared caching with `cached = false`; action-local consistency remains available while evaluating one model
action.

## Snapshots and checkpoints

Event-sourced models can bound reconstruction work:

```java
@Model(
    snapshotPeriod = 1000,
    maxSnapshotCount = 2,
    checkpointPeriod = 100)
record Account(@EntityId AccountId accountId, Money balance) {
}
```

- `snapshotPeriod` writes a durable snapshot after the configured number of model events;
- `maxSnapshotCount` bounds retained snapshots;
- `checkpointPeriod` keeps intermediate replay checkpoints where configured;
- stale snapshot or cache writes can never overwrite a higher `stateIndex`.

Snapshots are an optimization. The model stream remains authoritative for event-sourced loading unless publication was
explicitly configured to omit required history. Fluxzero does not retain a full direct document in every Model commit:
the direct search collection contains the current document, while `maxSnapshotCount` bounds the durable snapshots kept
for that Model. The event payloads remain the long-term history.

Loading an old Model with billions of unrelated namespace commits does not scan the namespace log. The Runtime selects
the Model's own stream and the SDK starts from its newest applicable snapshot or checkpoint, then replays only that
Model's remaining suffix. That suffix is transferred in membership- and byte-bounded pages; while the SDK applies one
page it may fetch exactly one following transport page, without delivering events out of order or retaining an
unbounded read-ahead queue. Choose snapshot periods from the expected per-Model history and state size; namespace age
by itself does not increase replay work. Long histories for one individual Model still deserve an explicit snapshot
and retention policy.

## Conflict policies

Clients may send the model state boundary they evaluated. If one of the relevant models changed before runtime commit:

- `ACCEPT` appends the original event and rebases documents, snapshots and relations on the merged current models;
- `FAIL` rejects and rolls back the complete action;
- `RETRY` rejects, reloads all action dependencies and reruns assertions, interceptors and applies within a bounded
  retry policy;
- `DEFAULT` inherits model, builder or property configuration and finally resolves to `ACCEPT`.

This is intentionally not the organizing principle of the model API. It is an optional consistency policy for the
uncommon case where multiple writers race on the same model.

## Logical and physical deletion

Returning `null` from `@Apply` logically deletes a model. Its current document and relations close, but its event
history remains and the same ID may later be recreated.

Logical parent deletion recursively deletes children whose relevant `@Parent` keeps the default
`deleteOnParentDeletion = true`, including pathless and shared-DAG descendants. Moving a child away or recreating the
parent in the same atomic commit prevents that lifecycle cascade.

Explicit hard deletion removes the selected model stream, heads, snapshots, cache and direct document. This is a
separate destructive operation: a physical descendant cascade must first be planned and confirmed. Detached
descendants remain discoverable through former-parent lineage
for lifecycle and GDPR cleanup.

Published audit events are not erased implicitly. Apply the application's event-log retention and data-protection
policies separately.

## Performance shape

Direct model commits are optimized around IDs:

- target streams and relation adjacency are distributed over Fluxzero's stable ID segments;
- JDBC writes are byte-bounded and batched rather than issued once per target;
- payload sharing is adaptive and used only when physical amplification justifies it;
- current and historical graph loads batch nodes by storage segment;
- ordinary direct loads do no relationship work.

Use a model with embedded `@Member` values when one small object graph genuinely belongs in one stream and document.
Split independently changing or searchable children into their own models.

<Aside type="note" title="Legacy aggregate persistence">
`@Aggregate` persists an older shared-root representation. It remains compatible throughout Fluxzero 1.x so existing
streams keep loading, but new manuals and examples use `@Model` exclusively. The aggregate API is scheduled for
deprecation in Fluxzero 2.0.
</Aside>
