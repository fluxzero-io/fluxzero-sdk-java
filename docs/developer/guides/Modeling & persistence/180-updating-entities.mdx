Model updates are immutable functions. `@AssertLegal` checks whether an action may happen, `@InterceptApply` can expand
or transform it, and `@Apply` returns the resulting model.

## Automatic command handling

An update that has enough information to identify its target models can be handled without a custom command handler:

<Tabs>
  <TabItem label="Java">
    ```java
    public record RenameProduct(ProductId productId, String name) {
        @AssertLegal
        void assertName(Product product) {
            if (name.isBlank()) {
                throw new IllegalArgumentException("Name is required");
            }
        }

        @Apply
        Product apply(Product product) {
            return new Product(productId, name);
        }
    }
    ```
  </TabItem>
  <TabItem label="Kotlin">
    ```kotlin
    data class RenameProduct(val productId: ProductId, val name: String) {
        @AssertLegal
        fun assertName(product: Product) {
            require(name.isNotBlank()) { "Name is required" }
        }

        @Apply
        fun apply(product: Product) = Product(productId, name)
    }
    ```
  </TabItem>
</Tabs>

Publishing `RenameProduct` as a command automatically executes the model action. Fluxzero determines the target from
`ProductId`, loads only that product, runs the assertions and applies, and commits the returned model.

No `loadAggregate`, command-to-event translation handler or marker interface is required.

Automatic handling can also be declared on the model:

```java
@Model
record Product(@EntityId ProductId productId, String name) {
    @Apply
    Product rename(RenameProduct command) {
        return new Product(productId, command.name());
    }
}
```

Register the model class as a handler when receiver methods are used. Payload-side applies are discovered from the
registered command payload.

## Calling the model pipeline explicitly

An explicit command handler can enter the same pipeline exactly once:

```java
@HandleCommand
String handle(RenameProduct command) {
    Fluxzero.assertAndApply(command);
    return "renamed";
}
```

Use this when the command must return a custom result or when automatic handling has been disabled. Metadata can be
attached without changing the update:

```java
Fluxzero.assertAndApply(command, Metadata.of("source", "admin"));
```

## Creating and deleting

An apply without a current value can create a model:

```java
record CreateProduct(ProductId productId, String name) {
    @Apply
    Product apply() {
        return new Product(productId, name);
    }
}
```

Returning `null` from a model apply logically deletes the target:

```java
record RemoveProduct(ProductId productId) {
    @Apply
    Product apply(Product product) {
        return null;
    }
}
```

The delete update is still an event according to the model's publication settings. The current model and direct search
document disappear, while the model stream remains available for audit and reconstruction. Returning `void` is not
allowed for model applies because it does not identify a resulting write.

Use the explicit `ModelRepository.deleteModel(...)` APIs for physical deletion. Cascading descendant deletion requires
an explicit, confirmed deletion plan.

## Reading other models during an action

Any directly referenced model can be injected into assertions, interceptors and applies:

```java
record PlaceOrder(
        OrderId orderId,
        InventoryId inventoryId,
        int quantity) {

    @AssertLegal
    void assertAvailable(Inventory inventory) {
        if (inventory.available() < quantity) {
            throw new IllegalStateException("Insufficient inventory");
        }
    }

    @Apply
    Order create(Inventory inventory) {
        return new Order(orderId, inventory.inventoryId(), quantity);
    }
}
```

`Inventory` is not required to be family of `Order`. It is loaded because the payload carries an `InventoryId`. A
direct dependency is read-only unless an apply returns that model.

When two properties refer to the same model type, qualify each parameter:

```java
@Apply
Account debit(@Association("sourceId") Account source) {
    return source.debit(amount);
}

@Apply
Account credit(@Association("destinationId") Account destination) {
    return destination.credit(amount);
}
```

## Parents and ancestors

If no direct payload property identifies an injected model, Fluxzero treats it as a read-only ancestor dependency. It
follows the stored relations at the action's pinned state boundary:

```java
@AssertLegal
void assertOwner(
        LineItem line,
        Order order,
        Customer customer) {
}
```

Parents, grandparents and further ancestors are loaded only when explicitly requested. Use
`@Association("billingLines")` when multiple ancestor edges of the same type are reachable; the qualifier then matches
the `@ParentId(path = "...")` edge.

## One action, multiple models

One update may return changes for several independent models. Fluxzero:

1. resolves and batch-loads every direct target and requested ancestor;
2. runs all assertions and interceptors;
3. stages every returned model and relation delta;
4. submits one model-action package to the runtime;
5. publishes the original domain event once globally while linking it to every target stream.

If evaluation fails, no target is committed. Conflict handling applies to the complete action:

- `ACCEPT` stores the original event and rebases derived documents, snapshots and relations on current model state;
- `FAIL` rolls the runtime action back and returns a conflict;
- `RETRY` rolls it back and performs a bounded complete reevaluation against freshly loaded models;
- `DEFAULT` inherits the application policy and ultimately falls back to `ACCEPT`.

Configure a default through `FluxzeroBuilder` or `fluxzero.model.conflictPolicy`, and override it on `@Model` or an
individual `@Apply`.

## Apply interceptors

`@InterceptApply` can reject, replace or expand an incoming update before applies run:

```java
record ImportOrder(List<ImportLine> lines) {
    @InterceptApply
    List<CreateLine> expand() {
        return lines.stream().map(ImportLine::toCreateLine).toList();
    }
}
```

Every emitted update runs through the same assertions and apply machinery. Interceptors may inject the same direct
models and ancestors as assertions and applies.

<Aside type="caution">
Do not perform irreversible external work inside an apply. It may run again during event sourcing or a conflict retry.
Publish follow-up messages from handlers or event handlers instead.
</Aside>

<Aside type="note" title="Legacy aggregate API">
Existing Fluxzero 1.x applications may continue to use `@Aggregate` and
`Fluxzero.loadAggregate(...).assertAndApply(...)`. New code should use model actions; the aggregate API is scheduled for
deprecation in Fluxzero 2.0.
</Aside>
