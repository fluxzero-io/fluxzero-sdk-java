import { Aside, Tabs, TabItem } from '@astrojs/starlight/components';

Fluxzero allows you to **track changes to your document store** using the `@HandleDocument` annotation.
This enables handlers to react to document updates in real time — much like handling events.

<Tabs>
  <TabItem label="Java">
    ```java
    @HandleDocument
    void handle(UserAccount user) {
        log.info("UserAccount {} was added or updated", user.getUserId());
    }
    ```
  </TabItem>
  <TabItem label="Kotlin">
    ```kotlin
    @HandleDocument
    fun handle(user: UserAccount) {
        log.info("UserAccount ${user.userId} was added or updated")
    }
    ```
  </TabItem>
</Tabs>

## How it works

Every time a document is (re)indexed, it receives a new message index (based on the timestamp of the update).
Handlers annotated with `@HandleDocument` will observe these updates as they pass through the **document log**.

<Aside type="caution">
When catching up from behind (e.g. in a replay), only the latest version of a document is retained per key.
Earlier intermediate versions are not visible to late consumers.
Use event handlers for business transitions that must each be processed. Document handling can reconcile pending
work only when the latest document retains all unfinished actions until they are acknowledged; see
[stateful handlers](../stateful-handlers/#choose-the-trigger-and-preserve-pending-work).
</Aside>

This makes `@HandleDocument` ideal for **live processing**, **projecting the latest known state**, or
**cache rebuilds**.

## Transforming stored documents

The examples below concern independent read-model documents. A typed Model parameter instead observes the canonical
searchable node and has a guarded, schema-only return contract: return its upcast value unchanged, with a higher
revision. `source = DocumentSource.MODEL_STATE` permits the same maintenance for internal, non-searchable DOCUMENT
state. Use Model commands to change business state or delete a Model.

A `Graph<Project>` parameter observes Project and its included descendants. Returning that Graph migrates evolved
canonical nodes in NONE, ASYNC and AWAIT. Select `graphMigration = GraphMigrationTarget.PROJECTION` for only the stored
ASYNC/AWAIT composition. See
[Testing Model migrations](../model-migration-tests).

`@HandleDocument` can also be used to **update documents in place**.

If the handler returns a **newer revision** of the document, Fluxzero will reindex and persist the result:

<Tabs>
  <TabItem label="Java">
    ```java
    @HandleDocument("users")
    UserAccount upgrade(UserAccount oldUser) {
        return new UserAccount(oldUser.getId(), normalizeEmail(oldUser.getEmail()));
    }
    ```
  </TabItem>
  <TabItem label="Kotlin">
    ```kotlin
    @HandleDocument("users")
    fun upgrade(oldUser: UserAccount): UserAccount {
        return UserAccount(oldUser.id, normalizeEmail(oldUser.email))
    }
    ```
  </TabItem>
</Tabs>

The returned value replaces the previous document (same ID), **only if** it has a **higher `@Revision`**.

<Aside type="tip">
This creates a powerful and durable upgrade path — ideal for data normalization, filling missing fields, or
applying business logic retroactively.
</Aside>

To **delete** a document from the store, return `null`:

<Tabs>
  <TabItem label="Java">
    ```java
    @HandleDocument("users")
    UserAccount upgrade(UserAccount user) {
        return user.isTestUser() ? null : user;
    }
    ```
  </TabItem>
  <TabItem label="Kotlin">
    ```kotlin
    @HandleDocument("users")
    fun upgrade(user: UserAccount): UserAccount? {
        return if (user.isTestUser) null else user
    }
    ```
  </TabItem>
</Tabs>

<Aside type="note">
Transformations are persisted reliably — even across application restarts — making this a great way to evolve your
document model safely.
</Aside>

## Use cases

- Auto-upcasting legacy documents
- Filling or correcting derived fields
- Cleaning up invalid or deprecated data
- Running background migrations or rehydration jobs
- Current-state analytics (use events when every change must be counted or logged)

## Handler configuration

The parameter selects what the handler observes:

| Declaration | Subscription |
| --- | --- |
| `@HandleDocument` with `Task` | Canonical searchable Task node |
| `@HandleDocument` with `Graph<Task>` | Task and its included descendants, in NONE, ASYNC and AWAIT |
| `@HandleDocument(source = DocumentSource.MODEL_STATE)` with `Task` | Internal maintained Task state, even without searchability |
| `@HandleDocument(documentClass = Task.class)` | Explicit node type when it cannot be inferred |
| `@HandleDocument("myCollection")` | An ordinary named document collection |

Metadata and message context may precede the payload. An ordinary payload before an injected Model/Graph continues
to select the ordinary document; use a leading `Graph<Task>` payload to select logical Graph updates. No source fallback
is performed. A missing required document source is a registration error.

A child change updates its own logical Graph and the included ancestor Graphs. Updating only Project's name does not
wake a `Graph<Task>` handler. `@GraphProperty` does not create subscriptions; observe `Graph<Project>` if that is the
scope you need. Moving a Task affects its own Graph and both old and new Project Graphs.

At NONE, registering a Graph handler activates a durable notification definition. Runtime then retains a small
update marker for each root, not its composed content. Query-only NONE does not activate this stream. The reader hydrates the
latest indexed Graph for that exact root. Updates may coalesce, and `previous()` is unavailable on this live view.
Deleting the root delivers a typed empty Graph. ASYNC/AWAIT read the stored aggregate; historical navigation still
requires the underlying Model history. Neither mode implies an atomic historical snapshot across all indexed nodes.

To switch an existing ASYNC/AWAIT definition to NONE, explicitly call
`modelRepository().registerGraphProjection(Root.class, true).join()` after changing the Model declaration.
Wait for its rebuild status to finish; this replaces aggregate bodies with markers. Cancelling a subscriber only
stops consumption. It does not unregister the durable definition.
A schema-only node rewrite durably requests a rebuild of the affected Graph definitions. This maintenance may notify
other roots in the same definition; it is not a business-event stream.

## Evolving a materialized Model Graph

Every node in a materialized Graph stores its own type and revision. When the Graph is read, the normal serializer
applies each Model type's ordinary `@Upcast` chain independently and lazily. There is no separate Graph upcaster and a
child Model does not inherit the root's revision.

If lazy read-time upcasting is sufficient, no document handler is needed. To durably rematerialize the evolved node
JSON for search, return the complete Graph from a dedicated handler:

<Tabs>
  <TabItem label="Java">
    ```java
    @HandleDocument
    Graph<Project> rematerialize(Graph<Project> graph) {
        return graph;
    }
    ```
  </TabItem>
  <TabItem label="Kotlin">
    ```kotlin
    @HandleDocument
    fun rematerialize(graph: Graph<Project>): Graph<Project> = graph
    ```
  </TabItem>
</Tabs>

Fluxzero migrates only nodes whose serialized type or revision evolved. Raise `@Revision` for a JSON-shape change.
The returned Graph must retain its injected values, root, state boundary, nodes and placements; business mutations
are rejected. Each evolved node is deduplicated and the SDK upcasts its **verified current canonical source**. It never
copies stale business values from the handled Graph into newer Modelstate. The write checks the complete Model head
and source proof; contention is re-read up to three writes, then fails handling for consumer retry. Deleted nodes
stay deleted. An already-migrated source is a no-op.

This works in NONE too. The Runtime records each changed node durably and refreshes only affected ancestor/root
projections or update markers, respecting search scope and depth. Schema-only revision changes do not restart full
scans. Changes to composition settings, participating Model types or an explicit rebuild still can.

Node writes complete before the handler completes. Derived projections follow durably; `AWAIT` continues to promise
completion for ordinary **Model commits**, not a schema-migration barrier. Verify new query paths after migration
catch-up. Migration is per node and idempotent after partial failure, not an atomic business operation over a Graph.
Model history, relationships and business-state indexes remain unchanged. Custom `DocumentSerializer` implementations
must provide `modelStateSnapshot` for immutable logical-state comparison; the built-in Jackson serializer does so.
The projection-only option below retains the earlier serializer contract.

For a deliberate projection-only migration, use the same Java or Kotlin handler with:

```java
@HandleDocument(graphMigration = GraphMigrationTarget.PROJECTION)
```

This preserves the earlier contract: compare the handled manifest and rewrite only its stored ASYNC/AWAIT
composition. NONE returns are observational. A later projection rebuilt from unchanged canonical sources may restore
old paths, so use this option only when maintaining a derived representation is intentional.

Deploy the compatible Runtime before enabling migration consumers. Older Runtimes supporting source rewrites can
still upcast nodes but may rebuild entire Modeltype projections; upgrade all projector instances for targeted work
and its schema fence. Existing type-only invalidations are drained through the legacy rebuild route. No defaults
version is needed: canonical-node migration is the default for Graph returns; the annotation provides the explicit
compatibility option.

## Replay for full collection migration

Want to upgrade all existing documents in a collection? Combine `@HandleDocument` with replays:

1. Create a handler method that returns upgraded documents
2. Increment the `@Revision` on the model class
3. Attach a custom consumer with `@Consumer(minIndex = 0, ...)`
4. Deploy temporarily until migration completes

This is a robust and rapid way to **reindex, clean, or refactor your stored documents** in-place.

<Tabs>
  <TabItem label="Java">
    ```java
    @Consumer(name = "reindex-users", minIndex = 0)
    class ReindexUsers {
        @HandleDocument("users")
        UserAccount upgrade(UserAccount legacyUser) {
            return fixLegacyState(legacyUser);
        }
    }
    ```
  </TabItem>
  <TabItem label="Kotlin">
    ```kotlin
    @Consumer(name = "reindex-users", minIndex = 0)
    class ReindexUsers {
        @HandleDocument("users")
        fun upgrade(legacyUser: UserAccount): UserAccount {
            return fixLegacyState(legacyUser)
        }
    }
    ```
  </TabItem>
</Tabs>

Once the transformation is complete, the handler can be safely removed.
