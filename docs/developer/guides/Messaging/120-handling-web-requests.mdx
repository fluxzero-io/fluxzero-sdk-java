Expose an HTTP endpoint by annotating a handler method. The return value becomes its response body, so you can use
the same application code and testing tools as for other messages.

For incoming provider callbacks, follow [Receive an external callback](/docs/guides/messaging/receiving-webhooks).

## Define an endpoint

<span id="example"></span>


<Tabs>
  <TabItem label="Java">

```java
@HandleGet("/hello")
String hello() { return "Hello, world!"; }
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@HandleGet("/hello")
fun hello() = "Hello, world!"
```

  </TabItem>
</Tabs>

Register the handler with your application, or use Spring's `@Component`. A `GET /hello` request then returns
`Hello, world!`. See [Hello world](/docs/getting-started/hello-world) for the local setup.

### Multiple paths or methods

Use the general-purpose `@HandleWeb` annotation if you want to support multiple paths, multiple methods, or define a custom method:

<Tabs>
  <TabItem label="Java">

```java
@HandleWeb(value = "/users/{userId}", method = {"GET", "DELETE"})
public CompletableFuture<?> handleUserRequest(WebRequest request, @PathParam String userId) {
    return switch (request.getMethod()) {
        case "GET" -> Fluxzero.query(new GetUser(userId));
        case "DELETE" -> Fluxzero.sendCommand(new DeleteUser(userId));
        default -> throw new UnsupportedOperationException();
    };
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@HandleWeb(value = ["/users/{userId}"], method = ["GET", "DELETE"])
fun handleUserRequest(request: WebRequest, @PathParam userId: String): CompletableFuture<*> {
    return when (request.method) {
        "GET" -> Fluxzero.query(GetUser(userId))
        "DELETE" -> Fluxzero.sendCommand(DeleteUser(userId))
        else -> throw UnsupportedOperationException()
    }
}
```

  </TabItem>
</Tabs>

<Aside type="tip">
To match all HTTP methods for a given path, use `HttpRequestMethod.ANY`. This is equivalent to `"*"` and will match any method.
</Aside>

<Tabs>
  <TabItem label="Java">

```java
@HandleWeb(value = "/users/{userId}", method = HttpRequestMethod.ANY)
public CompletableFuture<?> handleAllUserMethods(WebRequest request, @PathParam String userId) {
    // Handle any method (GET, POST, DELETE, etc.)
    ...
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@HandleWeb(value = ["/users/{userId}"], method = HttpRequestMethod.ANY)
fun handleAllUserMethods(request: WebRequest, @PathParam userId: String): CompletableFuture<*> {
    // Handle any method (GET, POST, DELETE, etc.)
    ...
}
```

  </TabItem>
</Tabs>

### Suppressing a response

If you want to listen to a `WebRequest` without returning a response—e.g. for monitoring or audit logging—use `passive = true`:

<Tabs>
  <TabItem label="Java">

```java
@HandlePost(value = "/log", passive = true)
public void log(WebRequest request) {
    logService.store(request);
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@HandlePost(value = "/log", passive = true)
fun log(request: WebRequest) {
    logService.store(request)
}
```

  </TabItem>
</Tabs>

### Graph responses

A handler may return a `Graph<T>` as composed JSON, including selected child paths and derived properties.
Use `@FilterContent` when the response needs viewer-specific filtering. See
[User-based content filtering](/docs/guides/data-control-and-serialization/user-based-content-filtering).

### Dynamic path parameters

Use `@PathParam` to extract dynamic segments from the URI:

<Tabs>
  <TabItem label="Java">

```java
@HandleGet("/users/{id}")
public UserAccount getUser(@PathParam String id) {
    return userService.get(id);
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@HandleGet("/users/{id}")
fun getUser(@PathParam id: String): UserAccount {
    return userService.get(id)
}
```

  </TabItem>
</Tabs>

If no name is provided to `@PathParam`, the parameter name is used by default.

Path parameters are percent-decoded once as UTF-8 after route matching and before type conversion.
For example, `order%3A1` becomes `order:1`; a literal `+` stays `+`. Encoded slashes (`%2F`)
belong to the parameter value and do not introduce route segments. Do not decode the injected value again.

### Other parameter annotations

You can also use these to extract other parts of the request:

- `@QueryParam` – extract query string values
- `@HeaderParam` – extract headers
- `@CookieParam` – extract cookies
- `@FormParam` – extract form-encoded values (e.g., from POST body)

<Aside type="note">
All of these annotations support implicit naming and type conversion.
</Aside>

Named body parameters that are missing or JSON `null` may fall back to another configured parameter source.
See <Jdoclink className="WebRequestContext" /> for source precedence and conversion.

### URI prefixing and composition with @Path

Use `@Path` on packages, classes, methods, and properties to construct URI paths. Paths are composed from outermost to innermost.

- A path starting with `/` resets the chain
- Empty paths use the simple name of the enclosing package or class
- If applied to a property (field or getter), its value is used as a dynamic segment

<Tabs>
  <TabItem label="Java">

```java
@Path
package my.example.api;

@Path("users")
public class UserHandler {

    @Path("{id}")
    @HandleGet
    public User getUser(@PathParam String id) { ... }
}
```

  </TabItem>
</Tabs>

This matches `/api/users/{id}`. If `@Path("/users")` had been used on the class instead, it would reset the prefix and match `/users/{id}`.

## Serving static files

Use `@ServeStatic` to serve static content directly from your app without an external web server:

<Tabs>
  <TabItem label="Java">

```java
@ServeStatic(value = "/web", resourcePath = "/static")
public class WebAssets {
}
```

  </TabItem>
</Tabs>

This serves files from `/static` (in classpath or filesystem) under the URI path `/web/**`.

### Features

- Supports classpath and file system resources
- Optional fallback file (e.g. for SPAs)
- Clean URLs for statically exported routes
- Smart `Cache-Control` headers
- GZIP and Brotli compression (if precompressed assets are present)

### Full annotation example

<Tabs>
<TabItem label="Java">

```java
@ServeStatic(
    value = "/assets",
    resourcePath = "/public",
    fallbackFile = "index.html",
    cleanUrls = true,
    immutableCandidateExtensions = {"js", "css", "svg"},
    maxAgeSeconds = 86400
)
```

</TabItem>
<TabItem label="Kotlin">

```kotlin
@ServeStatic(
    value = ["/assets"],
    resourcePath = "/public",
    fallbackFile = "index.html",
    cleanUrls = true,
    immutableCandidateExtensions = ["js", "css", "svg"],
    maxAgeSeconds = 86400
)
```

</TabItem>
</Tabs>

#### Parameters:

- `value`: Web URI path(s) to expose
- `resourcePath`: Filesystem or classpath root
- `fallbackFile`: Fallback for unknown paths (e.g. `index.html`)
- `cleanUrls`: Whether extensionless paths first try `<path>.html` and `<path>/index.html` before the fallback
- `immutableCandidateExtensions`: Enables long-lived caching for fingerprinted assets
- `maxAgeSeconds`: Cache duration for other resources

### Example: serving a React app

<Tabs>
<TabItem label="Java">

```java
@ServeStatic(value = "/app", resourcePath = "/static", fallbackFile = "index.html")
public class WebFrontend {
}
```

</TabItem>
<TabItem label="Kotlin">

```kotlin
@ServeStatic(value = ["/app"], resourcePath = "/static", fallbackFile = "index.html")
class WebFrontend
```

</TabItem>
</Tabs>

This serves:

- `/app/index.html`, `/app/main.js`, etc. from `/static`
- `/app/onboarding` from `/static/onboarding.html` or `/static/onboarding/index.html` when clean URLs are enabled
- Falls back to `index.html` for client-side routing

Set `cleanUrls = false` if extensionless paths should only try the exact path before the fallback.

<Aside type="tip">
Files are resolved from both the file system and classpath. File system files take precedence if both exist.
</Aside>

To restrict resolution:

- Use `classpath:/...` to only serve classpath files
- Use `file:/...` to only serve local files

### Combining static and dynamic handlers

You can mix `@ServeStatic` with dynamic handlers:

<Tabs>
<TabItem label="Java">

```java
@Path("/app")
@ServeStatic("static")
public class AppController {

    @HandleGet("/status")
    public Status getStatus() {
        return new Status("OK", Instant.now());
    }

    @HandlePost("/submit")
    public SubmissionResult submitForm(FormData data) {
        return formService.handle(data);
    }
}
```

</TabItem>
<TabItem label="Kotlin">

```kotlin
@Path("/app")
@ServeStatic("static")
class AppController {
    @HandleGet("/status")
    fun getStatus(): Status = Status("OK", Instant.now())

    @HandlePost("/submit")
    fun submitForm(data: FormData): SubmissionResult = formService.handle(data)
}
```

</TabItem>
</Tabs>

This will:

- Serve `/app/static/**` from the `static/` directory
- Also handle `/app/status` and `/app/submit` dynamically

<Aside type="note">
Static routes apply only to unmatched paths and can coexist with dynamic APIs in the same class or package.
</Aside>

## Why this design?

The Web Gateway receives public HTTP(S) and WebSocket traffic and forwards it through the Runtime as messages.
Your application handles those messages without exposing its own public HTTP server. Requests and responses share
the tracing and audit facilities used by commands and queries.

Applications control consumption through their trackers. Passive handlers can observe requests without producing
another response. You still need the appropriate authentication and authorization on exposed operations.

## Delivery and proxy configuration

HTTP requests use the same tracked processing model as other messages. A storage acknowledgement does not mean the
handler has finished, and retries after a failure can repeat work. Keep external side effects idempotent; see
[Delivery defaults and completion](/docs/guides/messaging/sending-messages/#delivery-defaults-and-completion).

### Proxy response header buffers

Most applications can use the default proxy settings. For measured header-buffer or memory pressure, the standalone
and embedded proxy expose these startup properties:

| Property | Environment variable | Purpose |
| --- | --- | --- |
| `fluxzero.proxy.responseHeaderBufferSize` | `FLUXZERO_PROXY_RESPONSE_HEADER_BUFFER_SIZE` | Initial response-header buffer size in bytes; normally 8192. |
| `fluxzero.proxy.http2MaxResponseHeaderSize` | `FLUXZERO_PROXY_HTTP2_MAX_RESPONSE_HEADER_SIZE` | HTTP/2 response-header limit in bytes; defaults to 16384. |
| `fluxzero.proxy.useOutputDirectByteBuffers` | `FLUXZERO_PROXY_USE_OUTPUT_DIRECT_BYTE_BUFFERS` | Use direct output buffers (`true`) or Java heap buffers (`false`). |

These tune buffer allocation, not response-body limits or the overall process-memory budget. Restart after changing
them and measure the effect on your workload. The initial capacity must be positive and no greater than the effective
response-header maximum. A capacity below that maximum can trigger Jetty's known HTTP/1.1 header-growth limitation;
matching it avoids that path at the cost of larger buffers. See [ProxyServer](https://fluxzero-io.github.io/fluxzero-sdk-java/javadoc/apidocs/io/fluxzero/proxy/ProxyServer.html) for the settings.

The HTTP/2 limit counts the complete uncompressed header list, including per-field overhead. It defaults to 16 KiB
regardless of defaults version; choose a larger explicit value when required. Oversized headers fail rather than
being truncated, and Jetty may close the connection, affecting other streams. The initial buffer setting applies
to HTTP/1; request-header limits are unchanged.
