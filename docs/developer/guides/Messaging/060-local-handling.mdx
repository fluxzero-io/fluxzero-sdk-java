Fluxzero supports both tracked and local message handling. **Local handlers** process messages in the publishing
thread, without persisting them or waiting for a tracker by default. Calls still go through the Fluxzero dispatch and
handler APIs; local handling does not mean calling the handler method directly.

Use a local handler when the calling application can perform the operation itself. For example, a greeting query
needs no stored delivery:

<Tabs>
  <TabItem label="Java">

```java
record GetGreeting(String name) implements Request<String> {}

@LocalHandler
class GreetingHandler {
    @HandleQuery
    String handle(GetGreeting query) { return "Hello, " + query.name() + "!"; }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
data class GetGreeting(val name: String) : Request<String>

@LocalHandler
class GreetingHandler {
    @HandleQuery
    fun handle(query: GetGreeting) = "Hello, ${query.name}!"
}
```

  </TabItem>
</Tabs>

Register the handler normally, then call `Fluxzero.queryAndWait(...)`. `@LocalHandler` can also be placed on a
method or package. Add `logMetrics = true` if you need metrics for these local calls; they are off by default.

## Require local handling

Use `@LocalOnly` sparingly on a payload or package when external publication would cross a security boundary. Fluxzero
then invokes local handlers only, suppresses `logMessage`, returns a failed future for an unhandled request and quietly
completes an unhandled non-request. Parent packages include their children; `@LocalOnly(false)` restores normal
fallback for a more specific package or payload type.

## Self-handling messages

For a reusable operation, put the handler on its payload. The same greeting then needs only one type, with no
registration or `@LocalHandler` annotation:

<Tabs>
  <TabItem label="Java">

```java
public record GetGreeting(String name) implements Request<String> {
    @HandleQuery
    String handle() { return "Hello, " + name + "!"; }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
data class GetGreeting(val name: String) : Request<String> {
    @HandleQuery
    fun handle() = "Hello, $name!"
}
```

  </TabItem>
</Tabs>

Call it through Fluxzero so validation, interceptors and message context still apply. Local self-handling is also
the default pattern for reusable external API operations; see
[Sending web requests](/docs/guides/messaging/sending-web-requests).

### Persisting a self-handling request

By default, such handlers are local in both synchronous and asynchronous fixtures. Use `@TrackSelf` only when the
command/query itself needs persisted delivery through the Runtime, its own consumer position or independent
replay/retry. Calling an external API, waiting for its response or wanting HTTP audit logs does not require it.
`@Consumer` configures that tracked handler when a custom configuration is needed:

<Tabs>
<TabItem value="Java" label="Java">

```java
@TrackSelf
@Consumer(name = "user-management")
public record GetGreeting(String name) implements Request<String> {

    @HandleQuery
    String handle() {
        return "Hello, " + name + "!";
    }
}
```

</TabItem>
<TabItem value="Kotlin" label="Kotlin">

```kotlin
@TrackSelf
@Consumer(name = "user-management")
data class GetGreeting(val name: String) : Request<String> {

    @HandleQuery
    fun handle(): String {
        return "Hello, $name!"
    }
}
```

</TabItem>
</Tabs>

When component-scanned (e.g., via Spring), `@TrackSelf` classes will be automatically discovered and registered. This works even if the annotation is placed on an interface rather than the concrete class—allowing for reusable handler patterns.

Use a shared `@TrackSelf` interface when several payload types should have the same tracked behavior.
Register the tracked payloads with the application that owns them; ordinary self-handling payloads remain local.
