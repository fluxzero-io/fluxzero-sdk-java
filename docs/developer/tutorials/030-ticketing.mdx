import { Tabs, TabItem } from '@astrojs/starlight/components';

Let's build the path from choosing seats to entering a concert. We will add a programme, reserve a group,
expire unpaid holds, accept payments and issue tickets. Then we will add delivery, admission, transfers,
refunds and the organizer's tools.

This continues [Building your first app](/docs/tutorials/first-app). The new challenge is coordinating several
independent lifecycles: a reservation can expire while a payment is still in progress, and a ticket can change
owner without changing the original purchase.

## Work through the app

Use the current example as your working project:

```shell
git clone https://github.com/fluxzero-io/fluxzero-sample-ticketing.git
cd fluxzero-sample-ticketing
fz dev
```

Rebuild the classes and methods below in their existing files. The checkout supplies the completed solution,
value types, session setup and React screens; source links show the full files around each excerpt.
The Kotlin tabs use the example's Java model and value types, so you can concentrate on each new behavior.

First try **Night Lights**: choose two places in the **Recital Hall** and reserve them. Sign in as
**demo-organizer** to explore **Operations** and **Entrance**. The local profile can complete a box-office sale
with a demo cash receipt; online Stripe checkout is a separate integration step later in this tutorial.

## Build the programme and seating layout

Start with places and performances. A `Venue` owns `Hall`s. Each hall has versioned `SeatingPlan`s containing
sections and seats. An `Event` describes the show; a `Performance` puts it at a particular time in a particular plan.

Implement `Performance` with two parent relationships:

The same performance is reachable through its show and its seating plan. It still has one identity and history.
Use the existing `CreateVenue`, `CreateHall`, `RegisterSeatingPlan` and `CreateEvent` commands to establish those
parents, then implement [SchedulePerformance](https://github.com/fluxzero-io/fluxzero-sample-ticketing/blob/main/src/main/java/io/fluxzero/ticketing/catalog/api/SchedulePerformance.java). Its application method creates the performance;
its rule requires a future start and a price for every section in the selected plan.

Keep the seating plan immutable once registered. Seats, adjacency and wheelchair/companion links belong to that
layout. Prices and available ticket types belong to the performance. This lets two dates use the same hall at
different prices without changing either date's layout.

## Reserve the whole group together

A reservation owns the buyer's selection, frozen admissions and prices, creation time, deadline and status.
Implement [ReserveTickets](https://github.com/fluxzero-io/fluxzero-sample-ticketing/blob/main/src/main/java/io/fluxzero/ticketing/booking/api/ReserveTickets.java) as an `@InterceptApply` decision. After checking the sales window
and selection, it returns the reservation and all required inventory changes together.

## Release an unpaid reservation

A hold lasts fifteen minutes, capped at the performance start. Store that deadline on the reservation and add
`ReservationDeadlines` as a handler. It schedules an owned expiry command for the current hold and cancels it when
the reservation leaves `HELD`.

Implement the expiry command itself:

<Tabs>
  <TabItem label="Java">

```java
@NoUserRequired
public record ExpireReservation(@Parent @NotNull ReservationId reservationId) {
    @InterceptApply Object ignoreStale(@Nullable Reservation reservation) {
        return reservation != null && reservation.status() == ReservationStatus.HELD && !Fluxzero.currentTime().isBefore(reservation.expiresAt())
                ? this : null;
    }
    @Apply Reservation apply(Reservation reservation) { return reservation.withStatus(ReservationStatus.EXPIRED); }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@NoUserRequired
data class ExpireReservation(@Parent @field:NotNull val reservationId: ReservationId) {
    @InterceptApply
    fun ignoreStale(@Nullable reservation: Reservation?): Any? =
        if (reservation != null && reservation.status() == ReservationStatus.HELD
            && !Fluxzero.currentTime().isBefore(reservation.expiresAt())) this else null

    @Apply
    fun apply(reservation: Reservation): Reservation =
        reservation.withStatus(ReservationStatus.EXPIRED)
}
```

  </TabItem>
</Tabs>

The inventory already tests the deadline when deciding whether stock is occupied. Availability therefore does
not depend on a timer arriving at precisely the deadline. The scheduled command updates the reservation's status.

## Record payment and issue tickets

Give [Payment](https://github.com/fluxzero-io/fluxzero-sample-ticketing/blob/main/src/main/java/io/fluxzero/ticketing/payment/api/model/Payment.java) its own Model under Reservation. A payment attempt can fail, succeed or need a
refund independently of whether the reservation still holds its places.

Implement [StartPayment](https://github.com/fluxzero-io/fluxzero-sample-ticketing/blob/main/src/main/java/io/fluxzero/ticketing/payment/api/StartPayment.java) to check ownership and an active online hold, then create a pending
payment for the reservation's total. Only the payment integration may report money received. In
`RecordPaymentSuccess`, first recognize a repeated confirmation, then decide whether this capture can still
confirm the reservation:

<Tabs>
  <TabItem label="Java">

```java
@NotNull @Valid Money amount) {
    @InterceptApply Object decide(Payment payment, Reservation reservation, Performance performance) {
        if (payment.captured() != null) {
            require(payment.captureReference().equals(captureReference) && payment.captured().equals(amount),
                    "Conflicting payment confirmation");
            return null;
        }
        Instant receivedAt = Fluxzero.currentTime();
        boolean accepted = reservation.holdsAt(receivedAt) && amount.equals(payment.expected());
        accepted = accepted && !performance.cancelled() && receivedAt.isBefore(performance.details().startsAt());
        var capture = new PaymentCaptured(paymentId, reservation.reservationId(), captureReference, amount, receivedAt, accepted);
        var changes = new ArrayList<Object>();
        changes.add(capture);
        if (accepted) changes.addAll(InventoryChanges.sell(reservation, performance, receivedAt));
        return changes;
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@InterceptApply
fun decide(payment: Payment, reservation: Reservation, performance: Performance): Any? {
    if (payment.captured() != null) {
        require(payment.captureReference() == captureReference && payment.captured() == amount,
            "Conflicting payment confirmation")
        return null
    }
    val receivedAt = Fluxzero.currentTime()
    val accepted = reservation.holdsAt(receivedAt) && amount == payment.expected()
        && !performance.cancelled() && receivedAt.isBefore(performance.details().startsAt())
    return buildList<Any> {
        add(PaymentCaptured(paymentId, reservation.reservationId(), captureReference, amount, receivedAt, accepted))
        if (accepted) addAll(InventoryChanges.sell(reservation, performance, receivedAt))
    }
}
```

## Connect checkout to Stripe

The booking rules now work without a payment provider. Add the adapter in `payment/stripe` with the existing
[BeginStripePayment](https://github.com/fluxzero-io/fluxzero-sample-ticketing/blob/main/src/main/java/io/fluxzero/ticketing/payment/stripe/api/BeginStripePayment.java) entry point. It starts the payment and records a provider-work request.

Use [StripePaymentProcess](https://github.com/fluxzero-io/fluxzero-sample-ticketing/blob/main/src/main/java/io/fluxzero/ticketing/payment/stripe/StripePaymentProcess.java), a `@Stateful` handler associated with `PaymentId`, to remember
which provider operation is in progress. `StripePaymentEffects` reacts to that stored state and sends the next
command or query. The provider attempt is separate from the business payment we just built.

### Create the external request

Implement `CreateStripeIntent` using `SendToStripe`, the app's shared authentication and request conventions:

```java
public record CreateStripeIntent(PaymentId paymentId, Money amount, String operationKey) implements SendToStripe<StripeIntent> {
    @HandleCommand StripeIntent handle() { return StripeIntent.from(send()); }

                        "payment_method_types[]", "card", "capture_method", "automatic",
                        "metadata[payment_id]", paymentId.getFunctionalId(), "metadata[operation_key]", operationKey)));
    }
}
```

## Admit the ticket once

A valid ticket still needs an admission decision. Add a `Gate` for the performance and a `CheckIn` Model parented
to the ticket. Implement `CheckInTicket` to check the performance, ticket validity, gate and staff permission,
then create the admission record:

<Tabs>
  <TabItem label="Java">

```java
@RequiresUser
public record CheckInTicket(@NotNull TicketId ticketId, @NotNull PerformanceId performanceId) {
    @AssertLegal Object allowed(Ticket ticket, Performance performance, @Nullable Gate gate) {
        require(ticket.performanceId().equals(performanceId), "Ticket belongs to another performance");
        require(ticket.status() == TicketStatus.VALID && !performance.cancelled(), "Ticket is not valid for admission");
        require(gate != null && gate.open(), "Admission is closed");
        return null;
    }
    @AssertLegal Object staff(User user) { return StaffPermission.forUser(performanceId, user, Permission.ADMISSION); }
    @Apply CheckIn apply(User user, Instant timestamp) {
        return new CheckIn(ticketId, timestamp, user.id());
    }
}
```
