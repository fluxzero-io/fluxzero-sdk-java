# Build a to-do app with Fluxzero

This tutorial builds projects and tasks as independently stored models. You will create and update them without
boilerplate command handlers, connect them with a relationship, search across that relationship and test the whole
flow.

## Project layout

Start with the Basic Starter for Java or Kotlin from [Installation](/docs/getting-started/installation). A small domain
can use this layout:

```text
io.fluxzero.todo
└── project
    ├── Project.java
    ├── Task.java
    ├── CreateProject.java
    ├── AddTask.java
    ├── CompleteTask.java
    └── ProjectQueries.java
```

Fluxzero does not require controller, service and repository layers around this code.

## Define a project

First define an immutable model with a typed ID and a details value. The ordinary `ProjectId` and `ProjectDetails`
value types are assumed below so the example can stay focused on Model behavior:

<Tabs>
  <TabItem label="Java">

```java
@Model(persistence = {ModelPersistence.EVENT_SOURCED, ModelPersistence.DOCUMENT})
public record Project(@EntityId ProjectId projectId,
                      ProjectDetails details,
                      UserId ownerId,
                      boolean archived) {
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@Model(persistence = [ModelPersistence.EVENT_SOURCED, ModelPersistence.DOCUMENT])
data class Project(
    @EntityId val projectId: ProjectId,
    val details: ProjectDetails,
    val ownerId: UserId,
    val archived: Boolean
)
```

  </TabItem>
</Tabs>

`@Model` gives each project ID its own persistence and lifecycle boundary. Here
Combining `EVENT_SOURCED` and `DOCUMENT` keeps event replay authoritative and also maintains a synchronous direct
search document. `@EntityId` identifies the Model.

## Create a project

The creation command carries its transition:

<Tabs>
  <TabItem label="Java">

```java
public record CreateProject(ProjectId projectId,
                            @Valid ProjectDetails details) {
    @Apply
    Project apply(Sender sender) {
        return new Project(
                projectId, details,
                sender.userId(), false);
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
data class CreateProject(
    val projectId: ProjectId,
    @field:Valid val details: ProjectDetails
) {
    @Apply
    fun apply(sender: Sender) =
        Project(projectId, details, sender.userId(), false)
}
```

  </TabItem>
</Tabs>

Send it like any command:

```java
Project result = Fluxzero.sendCommandAndWait(
        new CreateProject(
                projectId,
                new ProjectDetails("Website launch")));
```

Fluxzero discovers the `@Apply` method, resolves the target from `ProjectId`, checks that the project does not already
exist, applies the transition and commits it. The command itself becomes the stored and published model event.

<Aside type="tip">
No custom command handler or command-to-event translation is needed. Add a handler only when the action needs
orchestration beyond its model transition.
</Aside>

## Add an independently stored task

A task changes more frequently than its project and may need its own search and retention lifecycle. Give it its own
model and link it to a project:

<Tabs>
  <TabItem label="Java">

```java
@Model(persistence = {ModelPersistence.EVENT_SOURCED, ModelPersistence.DOCUMENT})
public record Task(@EntityId TaskId taskId,
                   @Parent(pathInParent = "tasks") ProjectId projectId,
                   TaskDetails details,
                   boolean completed) {
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
@Model(persistence = [ModelPersistence.EVENT_SOURCED, ModelPersistence.DOCUMENT])
data class Task(
    @EntityId val taskId: TaskId,
    @Parent(pathInParent = "tasks") val projectId: ProjectId,
    val details: TaskDetails,
    val completed: Boolean
)
```

  </TabItem>
</Tabs>

`@Parent` stores a current and temporal relationship edge. The stable `tasks` path tells graph loading and stitched
documents where children belong.

Now create a task while checking its unrelated parent model:

<Tabs>
  <TabItem label="Java">

```java
public record AddTask(TaskId taskId,
                      ProjectId projectId,
                      @Valid TaskDetails details) {
    @AssertLegal
    void assertProjectActive(Project project) {
        if (project.archived()) {
            throw new IllegalStateException(
                    "Cannot add tasks to an archived project");
        }
    }

    @Apply
    Task apply() {
        return new Task(
                taskId, projectId,
                details, false);
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
data class AddTask(
    val taskId: TaskId,
    val projectId: ProjectId,
    @field:Valid val details: TaskDetails
) {
    @AssertLegal
    fun assertProjectActive(project: Project) {
        check(!project.archived) {
            "Cannot add tasks to an archived project"
        }
    }

    @Apply
    fun apply() =
        Task(taskId, projectId, details, false)
}
```

  </TabItem>
</Tabs>

The typed `ProjectId` makes the project available to `@AssertLegal`; `TaskId` and the `Task` return type identify the
write target. Fluxzero loads only those two models. It does not load the project's other tasks.

## Complete a task

Updates receive the current target model:

<Tabs>
  <TabItem label="Java">

```java
public record CompleteTask(TaskId taskId) {
    @AssertLegal
    void assertNotCompleted(Task task) {
        if (task.completed()) {
            throw new IllegalStateException(
                    "Task was already completed");
        }
    }

    @Apply
    Task apply(Task task) {
        return new Task(
                task.taskId(),
                task.projectId(),
                task.details(),
                true);
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
data class CompleteTask(val taskId: TaskId) {
    @AssertLegal
    fun assertNotCompleted(task: Task) {
        check(!task.completed) {
            "Task was already completed"
        }
    }

    @Apply
    fun apply(task: Task) = task.copy(completed = true)
}
```

  </TabItem>
</Tabs>

If the assertion fails, Fluxzero commits nothing. If it succeeds, the task event, task stream membership, direct task
document and cache update belong to one model commit.

## Move a task

Moving a task is just a change to its relationship field:

```java
public record MoveTask(TaskId taskId,
                       ProjectId destinationId) {
    @AssertLegal
    void assertDestination(Project destination) {
        if (destination.archived()) {
            throw new IllegalStateException(
                    "Destination is archived");
        }
    }

    @Apply
    Task apply(Task task) {
        return new Task(
                task.taskId(), destinationId,
                task.details(), task.completed());
    }
}
```

The runtime closes the old relationship edge and opens the new one. Neither project nor any sibling task has to be
rewritten.

## Query direct documents

Search current task documents directly:

<Tabs>
  <TabItem label="Java">

```java
public record FindOpenTasks(String term) {
}

public final class ProjectQueries {
    @HandleQuery
    CompletableFuture<List<Task>> handle(
            FindOpenTasks query) {
        return Fluxzero.search(Task.class)
                .lookAhead(query.term(), "details/description")
                .match(false, "completed")
                .fetchAsync(100);
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
data class FindOpenTasks(val term: String)

class ProjectQueries {
    @HandleQuery
    fun handle(query: FindOpenTasks):
            CompletableFuture<List<Task>> =
        Fluxzero.search(Task::class.java)
            .lookAhead(query.term, "details/description")
            .match(false, "completed")
            .fetchAsync(100)
}
```

  </TabItem>
</Tabs>

Direct model search is synchronous with a successful model commit.

## Search through a parent

Relationship search can match a task on data held by its project:

<Tabs>
  <TabItem label="Java">

```java
import static io.fluxzero.common.api.search.constraints.MatchConstraint.match;

List<Task> launchTasks = Fluxzero.search(Task.class)
        .whereParent(
                Project.class,
                match("Website launch", "details/name"))
        .match(false, "completed")
        .fetchAll();
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
val launchTasks = Fluxzero.search(Task::class.java)
    .whereParent(
        Project::class.java,
        MatchConstraint.match("Website launch", "details/name")
    )
    .match(false, "completed")
    .fetchAll()
```

  </TabItem>
</Tabs>

`whereAncestor(...)` follows parents at any supported depth; its overload with `minDepth` and `maxDepth` lets you
constrain exactly how far it may traverse. This searches current direct documents and relationship edges. It does not
require a precomputed whole-project projection.

## Load a whole graph when needed

Most commands should load only their direct targets. A query that needs the whole project can explicitly load its
current graph:

```java
Graph<Project> graph = Fluxzero.loadGraph(projectId);
List<Task> tasks = graph.childModels("tasks", Task.class);
```

Graph search returns typed lazy graphs. It uses a configured materialized projection and otherwise stitches current
Model documents at query time:

```java
List<Graph<Project>> projects = Fluxzero.searchGraph(Project.class)
        .fetchAll();
```

For repeatedly queried large trees, enable a graph projection on the root:

```java
@Model(
    persistence = {ModelPersistence.EVENT_SOURCED, ModelPersistence.DOCUMENT},
    materializeGraph = true,
    graphProjection = @GraphProjection(
        collection = "project-overviews"))
public record Project(/* ... */) {
}
```

The projection is durable and asynchronous by default. Use `GraphProjectionCompletion.AWAIT` for an operation whose
command result should wait until affected root projections include that action. Use
`Fluxzero.searchGraph(Project.class, true)` only when a query must explicitly bypass the materialized projection and
stitch live.

## React to the exact event state

Event handlers can receive a directly affected model:

```java
public final class TaskNotifications {
    @HandleEvent
    void on(CompleteTask event,
            Task task,
            Graph<Task> graph) {
        // task is the state exactly after this event,
        // even if newer task events already exist.
        assert task.equals(graph.get());
    }
}
```

For a logical delete event, `Graph<Task>` is empty and exposes the deleted value through `previous()`. A bare non-null
`Task` only matches while a value exists.

## Test the application

The fixture executes the same model commit pipeline:

<Tabs>
  <TabItem label="Java">

```java
class TaskTest {
    private final ProjectId projectId =
            new ProjectId("launch");
    private final TaskId taskId =
            new TaskId("write-docs");

    @Test
    void completesTask() {
        TestFixture.create()
                .givenCommands(
                        new CreateProject(
                                projectId,
                                new ProjectDetails(
                                        "Website launch")),
                        new AddTask(
                                taskId, projectId,
                                new TaskDetails(
                                        "Write documentation")))
                .whenCommand(
                        new CompleteTask(taskId))
                .expectEvents(
                        new CompleteTask(taskId))
                .expectThat(fluxzero ->
                        assertTrue(
                                Fluxzero.loadModel(taskId)
                                        .get()
                                        .completed()));
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
class TaskTest {
    private val projectId = ProjectId("launch")
    private val taskId = TaskId("write-docs")

    @Test
    fun completesTask() {
        TestFixture.create()
            .givenCommands(
                CreateProject(
                    projectId,
                    ProjectDetails("Website launch")
                ),
                AddTask(
                    taskId, projectId,
                    TaskDetails("Write documentation")
                )
            )
            .whenCommand(CompleteTask(taskId))
            .expectEvents(CompleteTask(taskId))
            .expectThat {
                assertTrue(
                    Fluxzero.loadModel(taskId)
                        .get().completed
                )
            }
    }
}
```

  </TabItem>
</Tabs>

Add assertions for rejected commands, direct search and parent search as the application grows. Use a runtime
integration fixture for the same scenarios when you want to include the JDBC modelstream, relationship and document
stores.

## What you built

The application now has:

- automatic command handling through `@Apply`;
- independently stored project and task models;
- atomic actions that can read or update several models;
- a movable, temporally recorded project–task relationship;
- synchronous direct model search and relationship-aware search;
- exact model-state injection in event handlers;
- optional graph loading and materialized root projections;
- deterministic fixture tests without repository or service boilerplate.

Existing Fluxzero 1.x applications may still contain `@Aggregate` state. Treat it as legacy persisted state; new
features should use `@Model`, including the single-stream case where a model deliberately embeds `@Member` values.
