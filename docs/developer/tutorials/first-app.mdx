In this tutorial, we’ll build a simple to-do app that shows the core ideas of Fluxzero — one step at a time.
We’ll start from a blank slate and add features like creating tasks, organizing them into projects, querying data, and scheduling actions.

Each feature comes with a test, so you’ll see how Fluxzero works in practice, not just theory.

This is a Developer Guide for readers who want to work in the code. You can follow it yourself or with your agent.
For the builder workflow without code, start with [Local development](/docs/building/local-development).

---

## Why a to-do app?

To-do apps are simple and familiar, yet they cover all the essentials of a Fluxzero backend, like commands, queries and models.

To familiarize yourself with core concepts in Fluxzero, first [check them out](/docs/getting-started/core-concepts), if you haven't done so.

---

## Getting started

Have your coding agent create a new project called 'Todo', with root package `io.fluxzero.todo`, using the Basic Starter for Java or Kotlin
(see [Installation](/docs/getting-started/installation) for how).

The file comments below use `io.fluxzero.todo.project` with `command`, `query`, `model` and `notifications` packages
so the examples are easy to follow. You can organize your own application differently.

The examples use the Basic Starter's `Sender`, `UserId`, `Role`, and `RequiresRole` types. Keep its authentication
setup and type registration; they supply user context and short JSON type names for both Java and Kotlin.
Import those application types where needed. The [access-control guide](/docs/guides/messaging/role-based-access-control)
explains how to connect user identity and roles in your own app.

## Designing our app

Start with the thing someone wants to do: remember a task. A task needs a name, an assignee and a completion status.
We can create that useful piece first. Then we'll introduce projects to organize tasks, followed by search, web
endpoints and deadline notifications.

## Create a Task

Give each task its own identity:

<Tabs>
  <TabItem label="Java">

```java
// src/main/java/io/fluxzero/todo/project/model/TaskId.java
public final class TaskId extends Id<Task> {
    public TaskId(String id) {
        super(id);
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
// src/main/kotlin/io/fluxzero/todo/project/model/TaskId.kt
class TaskId(id: String) : Id<Task>(id)
```

  </TabItem>
</Tabs>

A typed ID keeps a Task ID distinct from a Project ID. It serializes as a string.
Now define the information we want to remember:

<Tabs>
  <TabItem label="Java">

```java
public record TaskDetails(@NotBlank String name) {
}

@Model
public record Task(@EntityId TaskId taskId,
                   @With TaskDetails details,
                   @With UserId assignee,
                   @With boolean completed) {
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
data class TaskDetails(@field:NotBlank val name: String)

@Model
data class Task(
    @EntityId val taskId: TaskId,
    val details: TaskDetails,
    val assignee: UserId,
    val completed: Boolean
)
```

  </TabItem>
</Tabs>

`@Model` tells Fluxzero to persist the Task. `@EntityId` identifies each instance. Models are immutable: changes return
a new value. The Java examples use Lombok's `@With` to generate those copies; Kotlin data classes provide `copy`.

### Create it with a command

A command represents the intent to create a task. It contains the task's ID and details, and an `@Apply` method that
creates its state:

<Tabs>
  <TabItem label="Java">

```java
public record CreateTask(@NotNull TaskId taskId,
                         @NotNull @Valid TaskDetails details) {
    @Apply
    Task create(Sender sender) {
        return new Task(taskId, details, sender.userId(), false);
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
data class CreateTask(
    @field:NotNull val taskId: TaskId,
    @field:NotNull @field:Valid val details: TaskDetails
) {
    @Apply
    fun create(sender: Sender) = Task(taskId, details, sender.userId, false)
}
```

  </TabItem>
</Tabs>

There are two pieces of business behavior here:

- `@NotNull` and `@Valid` check the input, including the task's nonblank name.
- `@Apply` creates the Task and assigns it to the sender. The sender comes from authenticated message context, not a user ID supplied by the client.

Fluxzero already rejects duplicate creation. Send the command and it handles the change automatically:

<Tabs>
  <TabItem label="Java">

```java
Fluxzero.sendCommandAndWait(new CreateTask(
        new TaskId("t1"), new TaskDetails("Submit tutorial")));
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
Fluxzero.sendCommandAndWait<Task>(CreateTask(
    TaskId("t1"), TaskDetails("Submit tutorial")))
```

  </TabItem>
</Tabs>

Fluxzero validates the command, runs its assertions, applies it and stores the accepted change. The same command
payload is published as an event, so other parts of the app can react. We don't need a separate command handler for
this state change. With Spring, keep these types inside the configured application scan; without Spring, register
your model command types with the application. In tests, command discovery happens automatically.

## Working with Tasks

A task is useful on its own. Let’s let its assignee change it, finish it, or cancel it.

We’ll add three commands:

- **AssignTask**: assigns a task to a different user.
- **CompleteTask**: marks a task as completed.
- **CancelTask**: cancels an unresolved task.

We’ll put the shared authorization rule on `TaskUpdate`. In this app, the assignee or an administrator may change a task.

<Tabs>
  <TabItem label="Java">

```java
public interface TaskUpdate {
    @NotNull TaskId taskId();

    @AssertLegal
    default void assertAuthorized(Task task, Sender sender) {
        if (!sender.isAuthorizedFor(task.assignee())) {
            throw new UnauthorizedException("Unauthorized for action");
        }
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
interface TaskUpdate {
    val taskId: TaskId

    @AssertLegal
    fun assertAuthorized(task: Task, sender: Sender) {
        if (!sender.isAuthorizedFor(task.assignee)) {
            throw UnauthorizedException("Unauthorized for action")
        }
    }
}
```

  </TabItem>
</Tabs>

The `@AssertLegal` method checks our business rule. An update's `@Apply` method takes an existing `Task`, so Fluxzero
already rejects a missing task. We don't need to write that existence check ourselves.

### Assign a Task

This command assigns a new user to the task:


</TabItem>
<TabItem value="Kotlin" label="Kotlin">

### Cancel a Task

To cancel a task, simply return `null` from your `@Apply` method:

<Tabs>
<TabItem value="Java" label="Java">

```java
// src/main/java/io/fluxzero/todo/project/command/CancelTask.java
public record CancelTask(@NotNull TaskId taskId) implements TaskUpdate {

    @AssertLegal
    void assertNotCompleted(Task task) {
        if (task.completed()) {
            throw new IllegalCommandException("Task has already completed");
        }
    }

    @Apply
    Task delete(Task task) {
        return null;
    }
}
```

</TabItem>
<TabItem value="Kotlin" label="Kotlin">

```kotlin
// src/main/kotlin/io/fluxzero/todo/project/command/CancelTask.kt
data class CancelTask(
    override val taskId: TaskId
) : TaskUpdate {

    @AssertLegal
    fun assertNotCompleted(task: Task) {
        if (task.completed) {
            throw IllegalCommandException("Task has already completed")
        }
    }

    @Apply
    fun delete(task: Task): Task? {
        return null
    }
}
```

</TabItem>
</Tabs>

<Aside type="note">
Returning <code>null</code> in an <code>@Apply</code> method logically deletes the Task and removes its current relationships. Its event history remains available.
</Aside>

## Testing with JSON

`TestFixture` runs commands and handlers locally and lets us describe a **given → when → then** flow.
You can pass ordinary Java or Kotlin objects to it. JSON files are an optional convenience: reusable inputs and
expected results keep the test focused on the behavior we want to check.

Create these files under `src/test/resources`:

```json title="project/create-task.json"
{
  "@class": "CreateTask",
  "taskId": "t1",
  "details": { "name": "Submit tutorial" }
}
```

```json title="project/assign-task.json"
{
  "@class": "AssignTask",
  "taskId": "t1",
  "newAssignee": "alex"
}
```

```json title="project/complete-task.json"
{
  "@class": "CompleteTask",
  "taskId": "t1"
}
```

The `@class` field identifies the payload type. The Basic Starter registers application types with `@RegisterType`,
so these short names work in both Java and Kotlin. Without that registration, use the fully qualified class name.
If two registered classes have the same name, include enough of the package to distinguish them.

<Tabs>
  <TabItem label="Java">

```java
class TaskFlowTest {
    TestFixture fixture = TestFixture.create();

    @Test
    void createsTask() {
        fixture.whenCommand("/project/create-task.json")
               .expectEvents("/project/create-task.json");
    }

    @Test
    void assigneeCompletesTask() {
        fixture.givenCommands("/project/create-task.json", "/project/assign-task.json")
               .whenCommandByUser("alex", "/project/complete-task.json")
               .expectEvents("/project/complete-task.json")
               .expectThat(f -> assertTrue(Fluxzero.loadModel(new TaskId("t1")).get().completed()));
    }

    @Test
    void completingMissingTaskFails() {
        fixture.whenCommand("/project/complete-task.json")
               .expectExceptionalResult(Entity.NOT_FOUND_EXCEPTION);
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
class TaskFlowTest {
    private val fixture = TestFixture.create()

    @Test
    fun createsTask() {
        fixture.whenCommand("/project/create-task.json")
            .expectEvents("/project/create-task.json")
    }

    @Test
    fun assigneeCompletesTask() {
        fixture.givenCommands("/project/create-task.json", "/project/assign-task.json")
            .whenCommandByUser("alex", "/project/complete-task.json")
            .expectEvents("/project/complete-task.json")
            .expectThat { assertTrue(Fluxzero.loadModel(TaskId("t1")).get()!!.completed) }
    }

    @Test
    fun completingMissingTaskFails() {
        fixture.whenCommand("/project/complete-task.json")
            .expectExceptionalResult(Entity.NOT_FOUND_EXCEPTION)
    }
}
```

  </TabItem>
</Tabs>

`TestFixture.create()` uses the starter's user provider. Unqualified commands use its system sender;
`whenCommandByUser("alex", ...)` exercises the same command as Alex. The last test uses the SDK's standard
missing-entity exception. Import `Entity` from `io.fluxzero.sdk.modeling` and `assertTrue` from JUnit's `Assertions`.

Passing an instance works just as well: replace the JSON argument to `whenCommand` with
`new CompleteTask(new TaskId("t1"))` in Java, or `CompleteTask(TaskId("t1"))` in Kotlin.
Use whichever form makes the scenario clearest.

As this app grows, we may want to organize related tasks into projects such as *Work*, *Groceries*, or *Side project*.
A project has a name, an optional description, and an owner:

For this app, let's decide that managers may create projects, while a project's owner controls its contents.
The Basic Starter includes a `Role` enum and a `@RequiresRole` annotation, so we can state the creation rule explicitly:

<Tabs>
  <TabItem label="Java">

```java

public record CreateProject(@NotNull ProjectId projectId,
                            @NotNull @Valid ProjectDetails details) {
    @Apply
    Project create(Sender sender) {
        return new Project(projectId, details, sender.userId());
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin

    @field:NotNull val projectId: ProjectId,
    @field:NotNull @field:Valid val details: ProjectDetails

}
```

  </TabItem>
</Tabs>

`@RequiresRole(Role.MANAGER)` checks the sender before applying the command. These are application-owned types from

available too, but enum roles keep this app’s role names checked by the compiler.
See [user access control](/docs/guides/messaging/role-based-access-control) for role configuration.

### Reusing business behavior

As with `TaskUpdate`, a shared interface can express the rule once: the project owner or an administrator may
modify the project. Both adding a task and changing the project details will use that rule.

We’ll introduce a `ProjectUpdate` interface:

<Tabs>
<TabItem value="Java" label="Java">

```java
// src/main/java/io/fluxzero/todo/project/command/ProjectUpdate.java
public interface ProjectUpdate {
    @NotNull ProjectId projectId();

    @AssertLegal
    default void assertAuthorized(Project project, Sender sender) {
        if (!sender.isAuthorizedFor(project.ownerId())) {
            throw ProjectErrors.unauthorized;
        }
    }
}
```

</TabItem>
<TabItem value="Kotlin" label="Kotlin">

```kotlin
// src/main/kotlin/io/fluxzero/todo/project/command/ProjectUpdate.kt
interface ProjectUpdate {
    val projectId: ProjectId

    @AssertLegal
    fun assertAuthorized(project: Project, sender: Sender) {
        if (!sender.isAuthorizedFor(project.ownerId)) {
            throw ProjectErrors.unauthorized
        }
    }
}
```

</TabItem>
</Tabs>

Implement this interface from `UpdateProject`, which changes the name or description, and `AddTask`, which creates
a task in the project:

<Tabs>
<TabItem value="Java" label="Java">

```java
public record UpdateProject(@NotNull ProjectId projectId,
                            @NotNull @Valid ProjectDetails details) implements ProjectUpdate {

    @Apply
    Project apply(Project project) {
        return project.withDetails(details);
    }
}
```

```java
public record AddTask(ProjectId projectId,
                      @NotNull TaskId taskId,
                      @NotNull @Valid TaskDetails details) implements ProjectUpdate {

    @Apply
    Task createTask(Project project, Sender sender) {
        return new Task(taskId, projectId, details, sender.userId(), false);
    }
}
```

</TabItem>
<TabItem value="Kotlin" label="Kotlin">

```kotlin
data class UpdateProject(
    @field:NotNull override val projectId: ProjectId,
    @field:NotNull @field:Valid val details: ProjectDetails
) : ProjectUpdate {

    @Apply
    fun apply(project: Project): Project {
        return project.copy(details = details)
    }
}
```

```kotlin
data class AddTask(
    override val projectId: ProjectId,
    @field:NotNull val taskId: TaskId,
    @field:NotNull @field:Valid val details: TaskDetails
) : ProjectUpdate {

    @Apply
    fun createTask(project: Project, sender: Sender): Task {
        return Task(taskId, projectId, details, sender.userId, false)
    }
}
```

</TabItem>
</Tabs>

The required `Project` parameter in `AddTask` ensures the parent exists before a task is created.
The shared interface checks whether the sender may modify that project. This ensures:

- Shared business logic for all updates is centralized.
- Each update command remains clean and focused on what it actually changes.

<Aside type="tip">
  You can further extend this pattern by introducing other shared interfaces, such as <code>ProjectQuery</code>, depending on your needs.
</Aside>

### Let project owners manage their tasks

We can now widen the task-update rule: a task's assignee, its project's owner, or an administrator may change it.
Replace `TaskUpdate` with the following version. The commands still need only a Task ID; Fluxzero resolves the
Project through the relationship.

<Tabs>
  <TabItem label="Java">

```java
public interface TaskUpdate {
    @NotNull TaskId taskId();

    @AssertLegal
    default void assertAuthorized(Task task, @Nullable Project project, Sender sender) {
        if (!sender.isAuthorizedFor(task.assignee())
            && (project == null || !sender.isAuthorizedFor(project.ownerId()))) {
            throw ProjectErrors.unauthorized;
        }
    }
}
```

  </TabItem>
  <TabItem label="Kotlin">

```kotlin
interface TaskUpdate {
    val taskId: TaskId

    @AssertLegal
    fun assertAuthorized(task: Task, project: Project?, sender: Sender) {
        if (!sender.isAuthorizedFor(task.assignee)
            && (project == null || !sender.isAuthorizedFor(project.ownerId))) {
            throw ProjectErrors.unauthorized
        }
    }
}
```

  </TabItem>
</Tabs>

These checks work for both standalone tasks and tasks in a project. `@Nullable` (or `?` in Kotlin) keeps the
assertion active when no project exists. The existing task commands keep their `@Apply` methods unchanged.

### How the request is routed

In Fluxzero, an HTTP request is just another message — like a command or query. Requests are logged by Fluxzero’s
web proxy and then dispatched to handlers in your application. Each method in this class handles an HTTP message.

These annotations:

- `@HandlePost`, `@HandleGet`, `@HandlePut`, etc.
  → Register HTTP routes on your endpoint (`/projects`, `/projects/{id}`, etc.).
- `@PathParam`
  → Binds a path segment (like <code>\{projectId\}</code>) to a method parameter.

Your handler methods can return results or `void`. Fluxzero manages the flow transparently:

1. **HTTP request is logged** — captured by Fluxzero's web proxy as a `WebRequest` message.
2. **App consumes it** — delivered like any other message.
3. **Handler runs** — your method processes the request.
4. **Response returned** — the result is sent back as a `WebResponse` to the client.

For more details, see the [handling web requests guide](/docs/guides/messaging/handling-web-requests/).

<Aside type="tip">
  Just like with other message handlers, you can inject the current user, full message, or message metadata into your
  handler using typed parameters like `Sender` or `WebRequest`.
</Aside>

First, we extend TaskDetails to include an optional deadline:

<TabItem value="Java" label="Java">

```java

                          Instant deadline) {
}
```

</TabItem>
<TabItem value="Kotlin" label="Kotlin">

```java
// src/main/java/io/fluxzero/todo/project/TaskScheduler.java
@Component
public class TaskScheduler {

    @HandleEvent
    void handle(CreateTask event) {
        if (event.details().deadline() != null) {
            Fluxzero.schedule(new TaskExpiry(event.taskId()),
                              "task-expiry-" + event.taskId(), event.details().deadline());
        }
    }

    @HandleEvent
    void handle(AddTask event) {
        if (event.details().deadline() != null) {
            Fluxzero.schedule(new TaskExpiry(event.taskId()),
                              "task-expiry-" + event.taskId(), event.details().deadline());
        }
```

### Sending to Slack

Now that we’ve scheduled TaskExpiry, let’s send a notification to a Slack channel when a tasks expires.

We’ll do this in a separate handler to keep responsibilities clear. This handler will load the task, check if it still exists, and then send a message to a Slack webhook (if configured):

<Tabs>
<TabItem value="Java" label="Java">

```java
// src/main/java/io/fluxzero/todo/project/notifications/SlackNotifier.java
@Component
@ConditionalOnProperty("slack.webhook.url")
public class SlackNotifier {

    @HandleSchedule
    void notifyAssignee(TaskExpiry expiry) {
        Task task = Fluxzero.loadCurrentGraph(expiry.taskId()).get();
        if (task != null && !task.completed()) {
            var message = String.format("Task '%s' has expired!", task.details().name());
            var slackUrl = ApplicationProperties.getProperty("slack.webhook.url");
            Fluxzero.sendWebRequest(
                WebRequest.post(slackUrl)
                          .payload(Map.of("text", message))
                          .build()
            );
        }
    }
}
```

</TabItem>

- SlackNotifier reacts to expirations.
- You could easily add other notifiers (e.g. email, WebSocket) that also react to the TaskExpiry schedule.

This design keeps your logic clean and your system honest: expiry is only acted on when the schedule triggers — and always based on the **latest task state**.

### Outgoing API calls

In Fluxzero, outgoing web requests — like sending a Slack message — are treated just like any other message.

When you call:

```java
Fluxzero.sendWebRequest(
    WebRequest.post(slackUrl)
              .payload(Map.of("text", message))
              .build()
);
```

By default, the request travels through Fluxzero's WebRequest log and forward proxy. This keeps external calls
observable alongside internal messages. You can also configure native HTTP dispatch; see
[sending web requests](/docs/guides/messaging/sending-web-requests) for transport and retry settings.

A remote service accepting a request is a separate effect from committing a model change. Check the returned future
when later behavior depends on that outcome, and design retryable integrations with an idempotency key where the
remote API supports one. A Slack webhook may be delivered again after a retry.

### Testing task notifications

Let's add a test to ensure that the Slack message goes out when a task deadline is missed.

<TabItem value="Java" label="Java">

```java
// src/test/java/io/fluxzero/todo/project/notifications/SlackNotifierTest.java
class SlackNotifierTest {
    String slackWebhookUrl = "http://slack.test";

    TestFixture fixture = TestFixture.create(
                        new TaskScheduler(),
            new SlackNotifier()
    ).withProperty("slack.webhook.url", slackWebhookUrl)
     .atFixedTime(Instant.parse("2026-01-01T00:00:00Z"));

    @Test
    void notifyAssigneeWhenDeadlineIsMissed() {
        fixture
                .givenCommands(
                        "/project/create-project.json",
                        "/project/add-task-30day-timeout.json"

                .whenTimeElapses(Duration.ofDays(30))

    @Test

                .givenCommands(

                        "/project/add-task-30day-timeout.json",
                        "/project/complete-task.json"
                )
```
