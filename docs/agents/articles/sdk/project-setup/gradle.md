Use this to validate or repair the Gradle project generated by `fz init`, or to update an existing Gradle project. Prefer `build.gradle.kts`, matching the supported CLI starters and tooling guidance.

Use the SDK version resolved by the project and documentation for that exact version. Do not upgrade or downgrade a project solely to match a documentation server. Upgrade only when requested or required by the task, after reviewing the intervening migration notes. For a new project, keep the CLI starter's concrete SDK choice. Verify a newly selected release against Fluxzero Packages; an existing resolved project and matching cached documentation do not require a fresh network lookup for every task. Explicit snapshot/local SDK development is a separate supported workflow, not a reason to silently select latest.

Resolve Spring Boot and, for Kotlin projects, Kotlin plugin versions from the existing project or their official plugin metadata. Pin concrete numeric `springBootVersion` and `kotlinVersion` values in `gradle.properties`; do not save placeholder tokens or dynamic versions. A `settings.gradle.kts` can make those pinned values available to the build plugin block:

```kotlin
pluginManagement {
    val springBootVersion: String by settings
    val kotlinVersion: String by settings
    val fluxzeroToolsVersion: String by settings
    repositories {
        maven("https://packages.fluxzero.io/maven")
        gradlePluginPortal()
        mavenCentral()
    }
    plugins {
        id("org.springframework.boot") version springBootVersion
        id("org.jetbrains.kotlin.jvm") version kotlinVersion
        id("org.jetbrains.kotlin.plugin.spring") version kotlinVersion
        id("org.jetbrains.kotlin.kapt") version kotlinVersion
        id("io.fluxzero.tools.gradle.plugin") version fluxzeroToolsVersion
    }
}
```

For a Java-only build, omit `kotlinVersion` and the three Kotlin plugin declarations instead of inventing an unused value.

Java setup:

```kotlin
plugins {
    java
    id("org.springframework.boot")
    id("io.fluxzero.tools.gradle.plugin")
}

val fluxzeroVersion: String by project

repositories {
    maven("https://packages.fluxzero.io/maven")
    mavenCentral()
}

dependencies {
    implementation(platform("io.fluxzero:fluxzero-bom:$fluxzeroVersion"))
    implementation("io.fluxzero:sdk")

    annotationProcessor(platform("io.fluxzero:fluxzero-bom:$fluxzeroVersion"))
    annotationProcessor("io.fluxzero:sdk")

    testImplementation(platform("io.fluxzero:fluxzero-bom:$fluxzeroVersion"))
    testImplementation("io.fluxzero:sdk") {
        artifact {
            classifier = "tests"
        }
    }
}

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(25)
    }
}
```

Generated Gradle starters may use Java 25. Install and use that declared toolchain for the generated project instead of lowering it to whatever the host already has. Java 25 is the minimum for this SDK release, including existing projects. Read the focused toolchain article before invoking the wrapper on a machine that may not have Java.

Kotlin setup adds kapt and Kotlin Spring support:

```kotlin
plugins {
    id("org.jetbrains.kotlin.jvm")
    id("org.jetbrains.kotlin.plugin.spring")
    id("org.jetbrains.kotlin.kapt")
    id("org.springframework.boot")
    id("io.fluxzero.tools.gradle.plugin")
}

val fluxzeroVersion: String by project

dependencies {
    implementation(platform("io.fluxzero:fluxzero-bom:$fluxzeroVersion"))
    implementation("io.fluxzero:sdk")
    implementation("com.fasterxml.jackson.module:jackson-module-kotlin")

    kapt(platform("io.fluxzero:fluxzero-bom:$fluxzeroVersion"))
    kapt("io.fluxzero:common")
    kapt("io.fluxzero:sdk")

    testImplementation(platform("io.fluxzero:fluxzero-bom:$fluxzeroVersion"))
    testImplementation("io.fluxzero:sdk") {
        artifact {
            classifier = "tests"
        }
    }
}
```

Use both `annotationProcessor(platform("io.fluxzero:fluxzero-bom:$fluxzeroVersion"))` and `annotationProcessor("io.fluxzero:sdk")` for Java projects so the annotation processor resolves through the Fluxzero BOM. Kotlin projects need both kapt artifacts: `common` provides type-registry processing, while `sdk` provides the request, OpenAPI, and web-parameter processors. A Kotlin build that contains only `kapt("io.fluxzero:common")` is incomplete even when ordinary compilation succeeds.

Use `mavenLocal()` only for local SDK or plugin development. Normal apps use Fluxzero Packages for Fluxzero artifacts, `mavenCentral()` for other dependencies, and the pinned Fluxzero BOM.

Optional Fluxzero IDP dependencies for authenticated apps:

Before adding them, inspect both Fluxzero Packages metadata documents:

```bash
curl -fsSL https://packages.fluxzero.io/maven/io/fluxzero/idp/client/maven-metadata.xml
curl -fsSL https://packages.fluxzero.io/maven/io/fluxzero/idp/test-support/maven-metadata.xml
```

Pin the newest stable numeric version present for both artifacts as `fluxzeroIdpVersion` in `gradle.properties`. Do not assume the Fluxzero SDK BOM supplies that version and do not copy it from an example.

```kotlin
val fluxzeroIdpVersion: String by project

dependencies {
    implementation("io.fluxzero.idp:client:$fluxzeroIdpVersion")
    testImplementation("io.fluxzero.idp:test-support:$fluxzeroIdpVersion")
}
```

Only add these when the app needs Fluxzero IDP login, bearer token validation, or local authenticated browser flows.

Keep the Fluxzero Gradle plugin applied at the root. Its `fluxzeroDevMetadata` task supplies the compiled classes and
classpath contract used by the dev server, and `fluxzeroDevTest` applies its selected test filters. Use the concrete
tools-plugin version generated by the CLI starter; when repairing an existing project, verify a current stable version
from the official Fluxzero CLI release/Fluxzero Packages rather than guessing or tying it to the SDK BOM.

Useful commands:

```bash
./gradlew fluxzeroDev
./gradlew fluxzeroDev -Pfluxzero.dev.background=true
```

An installed agent plugin uses `fz mcp` and explicitly calls its `start_dev` tool instead. Do not create a `runTestApp` task or add
`test-server`/`proxy` dependencies for the standard dev-server path. Keep wrapper tests for CI, release, or explicit
fallback verification.

Do not mix Maven and Gradle setup in the same project. If both build files exist, ask the user which one is authoritative.

Before final verification, confirm the effective dependencies still use the selected project version and the documentation context matches it.
