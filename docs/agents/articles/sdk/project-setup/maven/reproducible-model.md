Use this after choosing Maven and before writing domain code. A green build is not enough: the wrapper, parent/BOM structure, effective dependency management, and plugin versions must be reproducible on a clean machine.

## Pin a stable Maven runtime

Do not let an empty project inherit whichever `mvn` happens to be installed on the host. In particular, do not generate a wrapper without selecting the Maven distribution and accidentally preserve a prerelease such as Maven 4 RC.

Keep the wrapper generated by the CLI starter. If an existing project lacks a wrapper, generate a complete one with an explicitly selected supported stable Maven release. This is an example for Maven 3.9.9, not a claim that it is the latest release:

```bash
mvn wrapper:wrapper -Dmaven=3.9.9
./mvnw --version
```

Inspect `.mvn/wrapper/maven-wrapper.properties` and require its `distributionUrl` to name the intended stable release. Commit that file with `mvnw`, `mvnw.cmd`, and any wrapper JAR required by the selected wrapper mode. The wrapper plugin version and the Maven distribution version are different choices; seeing a stable `wrapperVersion` does not prove that `distributionUrl` is stable.

## Inspect the selected project release

Before writing the POM, retrieve the canonical metadata:

```bash
curl -fsSL https://packages.fluxzero.io/maven/io/fluxzero/fluxzero-bom/maven-metadata.xml
```

Use the SDK version resolved by the project and documentation for that exact version. Do not upgrade or downgrade a project solely to match a documentation server. Upgrade only when requested or required by the task, after reviewing the intervening migration notes. For a new project, keep the CLI starter's concrete SDK choice. Verify a newly selected release against Fluxzero Packages; an existing resolved project and matching cached documentation do not require a fresh network lookup for every task. Explicit snapshot/local SDK development is a separate supported workflow, not a reason to silently select latest.

Also retrieve the POM for that exact release:

```bash
release="$(./mvnw -q help:evaluate -Dexpression=fluxzero.version -DforceStdout)"
curl -fsSL "https://packages.fluxzero.io/maven/io/fluxzero/fluxzero-bom/$release/fluxzero-bom-$release.pom"
```

Use the numeric value only after verifying that `release` is nonempty and stable; the saved POM must contain the expanded number, never `$release`. Follow the BOM's declared parent POM to inspect inherited Spring Framework, Jackson, JUnit, and other shared dependency management. The direct `fluxzero-bom` POM manages Fluxzero modules; it does not itself list every framework line. If the application uses `proxy` or `test-server`, inspect those exact-release module POMs too: they import the Jetty BOM using the SDK parent's `jetty.version`. Do not infer the effective model from the direct BOM POM alone.

## Choose one compatible Spring Boot management shape

The shapes below are alternatives, not automatically compatible combinations. Do not combine them, and do not select the newest Spring Boot release independently of the Fluxzero BOM. A Boot parent or BOM that manages different Spring, Jackson, or JUnit lines can produce dozens of “Ignored POM import” effective-model warnings while compilation and tests still pass.

### Existing Spring Boot parent

Keep the project's concrete, supported `spring-boot-starter-parent` only when its managed framework lines are compatible with the just-fetched Fluxzero BOM. Let that parent manage standard plugin versions and add the Fluxzero BOM to this project's `dependencyManagement`:

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>io.fluxzero</groupId>
      <artifactId>fluxzero-bom</artifactId>
      <version>${fluxzero.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

This snippet assumes the saved POM already contains a concrete `fluxzero.version` matching the selected project release. Do not also import `spring-boot-dependencies`; the Boot parent already supplies it.

Before accepting this shape, compare the effective Spring Framework, Jackson, and JUnit versions with the selected Fluxzero release's inherited management. When `proxy` or `test-server` is present, also compare Jetty with those exact-release module POMs. If the Boot line is otherwise supported, align its documented version properties or add narrow direct managed-dependency entries using those source-backed versions, then rerun `validate`. Do not guess property names or copy overrides from an older SDK/Boot pair. If clean alignment is not possible, choose a compatible Boot line or the parentless shape instead.

### Parentless project

When organizational policy requires another parent or no parent, declare concrete `spring-boot.version` and `fluxzero.version` properties, import one Fluxzero BOM and one compatible Spring Boot dependencies BOM, and explicitly version build plugins that the Boot parent would otherwise manage:

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>io.fluxzero</groupId>
      <artifactId>fluxzero-bom</artifactId>
      <version>${fluxzero.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>${spring-boot.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

Do not also declare `spring-boot-starter-parent`. Pin `spring-boot-maven-plugin`, `maven-compiler-plugin`, and test plugins explicitly in this shape. Import order alone is not a compatibility strategy: compare the effective shared Spring/Jackson/JUnit lines with the selected Fluxzero release's parent management and, when relevant, Jetty with the exact `proxy` or `test-server` POM. Add a direct management override only for a deliberate, source-backed alignment, or choose a compatible Boot release. A model that merely ignores one conflicting BOM import is not clean.

## Validate the effective model

Run model checks before and after adding application code:

```bash
./mvnw --version
./mvnw validate
./mvnw help:effective-pom -Doutput=target/effective-pom.xml
./mvnw help:evaluate -Dexpression=fluxzero.version -q -DforceStdout
./mvnw test
```

Treat model-building warnings as defects even when tests pass. Run `validate` without `-q` and, when it summarizes model problems, rerun with `-e` to expose every conflict. Resolve duplicate dependency/plugin declarations, missing plugin versions, ignored BOM imports, conflicting BOM ownership, malformed parent coordinates, and expressions that Maven warns may become unsupported. Do not suppress or filter the warnings. Inspect the effective POM to confirm:

- the resolved Fluxzero SDK and annotation processor use the selected project release, with matching SDK documentation;
- the effective Spring Framework, Jackson, and JUnit lines agree with the selected Fluxzero release's inherited management and the chosen compatible Boot line;
- when `proxy` or `test-server` is used, the effective Jetty line is compatible with that exact-release module POM;
- build plugins have stable versions, either from the Boot parent or explicit parentless management;
- the Java release is consistent across compiler and runtime configuration.

Repeat these checks from a clean checkout or clean dependency cache when reproducibility is part of the acceptance criteria.

## Inspect the artifacts Maven actually resolved

Never assume the effective local repository is `~/.m2/repository`. CI, benchmark harnesses, Maven settings, and `-Dmaven.repo.local` commonly select a different path. Ask the running wrapper for both the effective repository and the pinned Fluxzero version:

```bash
repository="$(./mvnw -q help:evaluate -Dexpression=settings.localRepository -DforceStdout)"
version="$(./mvnw -q help:evaluate -Dexpression=fluxzero.version -DforceStdout)"
test -n "$repository" && test -d "$repository"
test -n "$version"
test -f "$repository/io/fluxzero/sdk/$version/sdk-$version.jar"
test -f "$repository/io/fluxzero/common/$version/common-$version.jar"
```

Use those exact paths for `jar tf` or `javap`, including the SDK tests classifier when checking `TestFixture`:

```bash
javap -classpath \
  "$repository/io/fluxzero/sdk/$version/sdk-$version.jar:$repository/io/fluxzero/common/$version/common-$version.jar" \
  io.fluxzero.sdk.persisting.eventsourcing.Apply \
  io.fluxzero.sdk.publishing.routing.RoutingKey \
  io.fluxzero.common.api.Metadata

javap -classpath \
  "$repository/io/fluxzero/sdk/$version/sdk-$version-tests.jar:$repository/io/fluxzero/sdk/$version/sdk-$version.jar" \
  io.fluxzero.sdk.test.Then io.fluxzero.sdk.test.ResultValidator
```

If `help:evaluate` emits anything except the value, rerun without `-q` and resolve the model error instead of stripping arbitrary output. Inspecting an ambient source checkout or a similarly named JAR elsewhere does not prove what this project compiles against.
