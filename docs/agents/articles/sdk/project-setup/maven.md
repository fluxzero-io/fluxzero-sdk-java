Use this to validate or repair the Maven project generated by `fz init`, or to update an existing Maven project. Keep the POM focused, then add domain code through the recipes. Prefer the current `io.fluxzero:sdk` artifact; older prose that names `fluxzero-sdk` is stale.

For an existing project, keep its supported Java 21-or-newer toolchain. For a CLI-generated project, keep the starter's declared JDK and install it when missing instead of lowering the compiler release. In either case, keep the Fluxzero annotation processor explicit so generated metadata stays reliable. Read the focused toolchain article before invoking the wrapper on a machine that may not have Java.

When selecting a new SDK release or verifying an upgrade, consult the Fluxzero Packages metadata for the Fluxzero BOM:

```bash
curl -fsSL https://packages.fluxzero.io/maven/io/fluxzero/fluxzero-bom/maven-metadata.xml
```

Use the SDK version resolved by the project and documentation for that exact version. Do not upgrade or downgrade a project solely to match a documentation server. Upgrade only when requested or required by the task, after reviewing the intervening migration notes. For a new project, keep the CLI starter's concrete SDK choice. Verify a newly selected release against Fluxzero Packages; an existing resolved project and matching cached documentation do not require a fresh network lookup for every task. Explicit snapshot/local SDK development is a separate supported workflow, not a reason to silently select latest.

Keep the complete Maven Wrapper generated by the CLI. If an existing project lacks a wrapper, generate one with an explicitly selected stable Maven distribution. Maven 3.9.9 is a known-working example:

```bash
mvn wrapper:wrapper -Dmaven=3.9.9
./mvnw --version
```

Commit `mvnw`, `mvnw.cmd`, and `.mvn/wrapper/maven-wrapper.properties` together, plus the wrapper JAR when the chosen wrapper mode requires it. Inspect `distributionUrl`: the wrapper plugin version is not the Maven distribution version. Do not create a shell script that only runs `mvn "$@"`, and do not leave an empty `.mvn` directory: that silently uses whichever Maven version happens to be installed on the machine and makes the build non-reproducible. Read reproducible Maven model guidance before choosing Spring Boot parent versus parentless BOM management.

Generated Maven starters may set a newer release such as Java 25. Use that declared release for the generated project, but do not copy it into an existing Java 21+ app unless the user wants the toolchain upgrade.

After selecting the concrete, Fluxzero Packages-verified `fluxzero.version`, use it for dependency management:

```xml
<properties>
  <java.version>21</java.version>
</properties>

<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>io.fluxzero</groupId>
      <artifactId>fluxzero-bom</artifactId>
      <version>${fluxzero.version}</version>
      <scope>import</scope>
      <type>pom</type>
    </dependency>
  </dependencies>
</dependencyManagement>
```

The saved POM must also contain the concrete selected `fluxzero.version`. It is intentionally not hard-coded in this article: preserve the project's version, or verify a newly chosen release against Fluxzero Packages.

Add the public repository for both dependencies and Maven plugins inside `<project>` (merge existing repository
sections rather than duplicating them). Maven Central remains available for third-party dependencies:

```xml
<repositories>
  <repository>
    <id>fluxzero</id>
    <url>https://packages.fluxzero.io/maven</url>
    <snapshots><enabled>false</enabled></snapshots>
  </repository>
</repositories>
<pluginRepositories>
  <pluginRepository>
    <id>fluxzero-plugins</id>
    <url>https://packages.fluxzero.io/maven</url>
    <snapshots><enabled>false</enabled></snapshots>
  </pluginRepository>
</pluginRepositories>
```

Core dependencies:

```xml
<dependencies>
  <dependency>
    <groupId>io.fluxzero</groupId>
    <artifactId>sdk</artifactId>
  </dependency>

  <dependency>
    <groupId>io.fluxzero</groupId>
    <artifactId>sdk</artifactId>
    <classifier>tests</classifier>
    <scope>test</scope>
  </dependency>
</dependencies>
```

Keep the normal Spring Boot dependencies and test dependencies in the project as usual. The CLI starter includes `spring-boot-starter`, `spring-boot-starter-test`, and `spring-boot-maven-plugin`.

Optional Fluxzero IDP dependencies for authenticated apps:

Resolve the IDP version independently from the SDK BOM. Inspect the Fluxzero Packages metadata for both artifacts and choose the newest stable numeric version present in both lists:

```bash
curl -fsSL https://packages.fluxzero.io/maven/io/fluxzero/idp/client/maven-metadata.xml
curl -fsSL https://packages.fluxzero.io/maven/io/fluxzero/idp/test-support/maven-metadata.xml
```

Write that exact common version into the `fluxzero-idp.version` property before adding the dependencies. Do not guess it, inherit it from the Fluxzero SDK BOM, or copy it from an example. If the metadata cannot be verified, leave the optional dependencies out and report the unresolved authentication dependency instead of saving a placeholder.

```xml
<dependency>
  <groupId>io.fluxzero.idp</groupId>
  <artifactId>client</artifactId>
  <version>${fluxzero-idp.version}</version>
</dependency>
<dependency>
  <groupId>io.fluxzero.idp</groupId>
  <artifactId>test-support</artifactId>
  <version>${fluxzero-idp.version}</version>
  <scope>test</scope>
</dependency>
```

Only add these when the app needs Fluxzero IDP login, bearer token validation, or local authenticated browser flows.

Java compiler setup:

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <release>${java.version}</release>
    <parameters>true</parameters>
    <annotationProcessorPaths>
      <path>
        <groupId>io.fluxzero</groupId>
        <artifactId>sdk</artifactId>
        <version>${fluxzero.version}</version>
      </path>
    </annotationProcessorPaths>
  </configuration>
</plugin>
```

Kotlin projects add a kapt execution that points at the Fluxzero SDK annotation processor:

```xml
<plugin>
  <groupId>org.jetbrains.kotlin</groupId>
  <artifactId>kotlin-maven-plugin</artifactId>
  <configuration>
    <jvmTarget>${kotlin.compiler.jvmTarget}</jvmTarget>
    <javaParameters>true</javaParameters>
  </configuration>
  <executions>
    <execution>
      <id>kapt</id>
      <goals>
        <goal>kapt</goal>
      </goals>
      <configuration>
        <annotationProcessorPaths>
          <annotationProcessorPath>
            <groupId>io.fluxzero</groupId>
            <artifactId>sdk</artifactId>
            <version>${fluxzero.version}</version>
          </annotationProcessorPath>
        </annotationProcessorPaths>
      </configuration>
    </execution>
  </executions>
</plugin>
```

Kotlin Maven projects should also declare `src/main/kotlin` and `src/test/kotlin` source directories, use Kotlin Spring/all-open support, and keep Java `package-info.java` files for package-level Fluxzero annotations. Do not delete the Java package-info file just because most sources are Kotlin.

Keep the Fluxzero Maven plugin from the generated starter. It provides the project-local dev launcher and keeps the
existing agent-manual sync goal available. Use the concrete plugin version generated by the current CLI; when repairing
an existing project, verify a current stable tools release from Fluxzero Packages rather than assuming it follows the SDK
BOM.

```bash
./mvnw fluxzero:dev
./mvnw fluxzero:dev -Dfluxzero.dev.background=true
```

An installed agent plugin uses `fz mcp` and explicitly calls its `start_dev` tool instead. Do not configure `exec-maven-plugin`, a
test-classpath `TestApp`, or `test-server`/`proxy` dependencies for the standard dev-server path. The focused manual
runtime article preserves that fallback when the dev server is genuinely unavailable.

The same Fluxzero Maven plugin provides package publishing when requested. Prefer Maven settings or environment
variables for credentials; do not put tokens in the POM.

```bash
mvn -B package fluxzero:publish-package
```

Run `./mvnw validate` before adding application code and treat effective-model warnings as build defects. Pin versions for explicitly declared build plugins; a passing test run does not make a malformed or machine-dependent Maven model acceptable.

Before final verification, confirm the effective dependencies still use the selected project version and the documentation context matches it.
